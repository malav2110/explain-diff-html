jsdom 30.1.0: the tree, its caches, and closed documents

jsdom 30.1.0 stores tree links on each node in place of the symbol-tree library, runs node insertion in the DOM Standard's order, and ties cached queries, queued tasks, and requests to the tree and document lifetimes they depend on.

jsdom/jsdom v30.0.1..v30.1.0 at 556b11fc, explained 2026-11-16. References link to this commit.

Background

New to jsdom's internals? Expand for the deeper background.

jsdom implements the DOM and HTML standards in JavaScript, so code written for browsers can run in Node.js, most often inside a test runner. Each object a page script touches, such as a Node or the Window, is a wrapper generated from a Web IDL file such as Document.webidl. The wrapper forwards every call to an implementation object, called an impl, under lib/jsdom/living/. NodeImpl is the impl base class for all nodes, and DocumentImpl extends it. Names that start with an underscore, like _insert(), are internal to jsdom; page scripts never see them.

The DOM Standard writes each operation as an algorithm with numbered steps. Its insert algorithm places nodes in the tree and calls hooks that other standards fill in:

  • The insertion steps run for each inserted node while the insertion is still under way. They must not run page scripts.
  • The children changed steps run on a parent after its child list changes. The children inserted steps, proposed in whatwg/dom pull request 1460, run only after an insertion.
  • The post-connection steps run once every node of the insertion is in place. HTML uses them to prepare a <script>, which means running its prepare-the-script algorithm to decide whether and when the script runs, and to start loading an <iframe>.

A live collection, such as node.childNodes or the result of getElementsByTagName(), shows the current tree each time it is read. A Range marks a span of the document with two boundary points, each a node and an offset, and the offset inside an element is a child index. A named property lets a script reach an element by its name or id attribute, as in window.myFrame. A task is work queued to run later on the event loop; HTML ties each task to a document and never runs a task whose document has been destroyed.

A WeakRef points at an object without keeping it alive. Its deref() returns undefined once the garbage collector has reclaimed the object. A FinalizationRegistry runs a callback some time after a registered object is reclaimed.

jsdom measures itself against the web platform tests, the shared suite browsers run. Tests written in this repository for later submission upstream live under test/web-platform-tests/to-upstream/.

Version 30.1.0 bundles 94 commits, so this page groups them by theme. The release notes describe performance work on tree mutation, collections, styles, events, and memory, and correctness issues fixed "along the way". The larger commits carry long messages that state their reasons, and the page takes the why from those messages, naming each commit where it does.

The release removes 256 lines that reference domSymbolTree, so most files in the first theme below change only by swapping those calls.

Insertion side effects ran through hooks jsdom had named for itself. _attach() walked a subtree newly inserted into the document tree and set an _attached flag on each node. Element classes overrode it, and HTMLScriptElement started its script there.

Child list changes ran a second hook. A memoized query is a stored result of a call such as getElementsByTagName("li"), so a second call with the same argument returns the same live collection. A generic wrapper, memoizeQuery in lib/jsdom/utils.js, kept those results in a _memoizedQueries object that every node created in its constructor. After every child list change, _modified() bumped a _version counter on the node and on each ancestor, rebuilt the node's childNodes and children lists on the spot, and replaced the memoized queries up the ancestor chain. Each live collection stores the _version it last saw and rebuilds when its owner node's number is higher.

Closing a window took the document apart. window.close() emptied document.body, called document.close(), and deleted window._document. Internal tasks, such as firing message after postMessage(), were bare Node.js setTimeout() or setImmediate() calls that no document tracked.

Resource loads go through undici, the HTTP client package jsdom depends on. undici sends each request through a dispatcher, here JSDOMDispatcher, and reports its progress to a handler object. A redirected request is a chain of hops, and each hop has its own transport controller, the object that can abort that hop. Tests can also answer requests themselves through requestInterceptor(), a helper jsdom exports.

The Code walkthrough's flow map starts where a page script changes the tree, at appendChild() or insertBefore(). Both reach NodeImpl._preInsert(), which validates the call and hands the node to _insert(), jsdom's version of the DOM Standard's insert algorithm.

Key concept In the document tree is not the same as connected. A node is in the document tree when following parents alone reaches the document. It is connected when that walk may also jump from a shadow root to its host. A node inside a shadow tree attached to the document is therefore connected but not in the document tree. This release renames the cached flag _attached to _isInDocumentTree; its commit, 1337f63a, says the new name keeps callers from confusing it with connectedness.

Intuition

One idea runs through the release: do work once what it depends on is settled, and check a cached answer against what can make it wrong when the answer is used. That framing is this page's summary, not a phrase from the release notes.

Sibling indexes show the cache half. A script fills a <ul> with six <li> elements, a through f, by calling appendChild() six times. Each append records the new child's index, 0 through 5, because appending never moves an existing child. Then the script inserts x before c. Every index from c onward is now one too small, so the parent marks its index cache as stale and does nothing more.

Later a Range needs e's index. jsdom does not trust e's stored 4. It walks from the first child, records a, b, x, c, and d, reaches e at 5, and stops there:

ul, cache marked stale by the insert
a0, recorded on the walk

b1, recorded

x2, recorded

c3, recorded

d4, recorded

e5, the index asked for

fnever walked: the walk stops at e

Script timing shows the other half. A script appends a fragment that holds an inline <script> followed by <p id="x">. In 30.0.1 the per-node loop in _insert() called _attach() on each node as it went in. jsdom's script queue ran an inline script immediately when no earlier script was waiting, so the script ran before the <p> was in the tree, and document.getElementById("x") inside it returned null. In 30.1.0 the per-node loop only places nodes and runs insertion steps. The script runs in a post-connection step after both nodes are in, and only if it is still connected then, so it finds the <p>.

Child lists and memoized queries follow the cache half. A mutation calls _invalidateCaches(), which replaces _modified() and clears what the mutation affects. Rebuilding waits for whoever reads next:

Appending one item to a list that a script holds as ul.children

ul.appendChild(li)
[li]
_insert() links li
ul
_invalidateCaches() bumps _version on ul and its ancestors
list emptied
ul.children holds nothing until read
length read
one rebuild, on demand

window.close() works the same way. It no longer empties the document; it sets _isDestroyed on it, and every task queued for that document checks the flag when its turn comes and does nothing. Requests follow suit: cancellation belongs to the request, not to whichever redirect hop is in flight, so a hop that starts after window.stop() is aborted as soon as it begins.

Code walkthrough

Flow, summarized at theme level: appendChild() → tree links in dom-tree.js → _insert() with its insertion and post-connection steps → the caches a mutation clears. Later themes cover computed styles, closed documents, request cancellation, and smaller fixes.

A Links object and a lazily rebuilt index cache

Commit d555e61f adds lib/jsdom/living/helpers/dom-tree.js in place of the symbol-tree package, which package.json drops. A node gets a Links object on node._links the first time it joins a tree or gains a child. It holds the parent, the siblings, the first and last child, the child count, and the index-cache fields:

lib/jsdom/living/helpers/dom-tree.js:13-24

class Links {
  parent = null;
  previousSibling = null;
  nextSibling = null;
  firstChild = null;
  lastChild = null;
  childCount = 0;
  // null: append-time indexes are valid; undefined: they need rebuilding;
  // array: a lazily indexed prefix of the children.
  cachedChildren = null;
  cachedIndex = -1;
}

The getters on NodeImpl read those fields directly. A node that was never inserted answers from the ?? null fallback without allocating anything:

lib/jsdom/living/nodes/Node-impl.js:280-286

  get parentNode() {
    return this._links?.parent ?? null;
  }

  _treeIndex() {
    return treeHelpers.treeIndex(this);
  }

Each child's cachedIndex is the index it got when appended. The parent's cachedChildren holds one of three values. null means every child's cachedIndex is still right, and the helper appendChild() in dom-tree.js keeps that value by giving the new child the next index. undefined means a middle insertion or removal made the indexes stale; the helper insertBefore() sets it. An array holds the first children in order, rebuilt only as far as someone has asked. The append and insert code is at lib/jsdom/living/helpers/dom-tree.js:299-300 and lib/jsdom/living/helpers/dom-tree.js:318-324. treeIndex(), which returns a node's position among its siblings, reads the cache:

lib/jsdom/living/helpers/dom-tree.js:268-286

  if (parentData.cachedChildren === null) {
    return data.cachedIndex;
  }
  const cached = parentData.cachedChildren ||= [];
  // A shifted node can retain an old index inside the rebuilt prefix. Check
  // identity as well as the index before using it.
  if (cached[data.cachedIndex] === node) {
    return data.cachedIndex;
  }
  let child = cached.length === 0 ? parentData.firstChild : cached.at(-1).nextSibling;
  while (child !== node) {
    child._links.cachedIndex = cached.length;
    cached.push(child);
    child = child.nextSibling;
  }
  data.cachedIndex = cached.length;
  cached.push(node);
  return data.cachedIndex;
}

The check cached[data.cachedIndex] === node refuses a stored index unless the rebuilt prefix holds this very node at that position. In the Intuition example the prefix starts empty, so e's stored 4 is refused and the walk runs. The helper remove() truncates the array, which also drops the cache's references to a removed subtree, so a parent that stays alive does not keep removed children alive; see lib/jsdom/living/helpers/dom-tree.js:345-351.

The same file supplies the tree iterators. Its ShadowIncludingIterator replaces recursive generators in shadow-dom.js with an explicit stack. Per the commit message, that keeps the traversal order and stops insertion steps from repeating when a callback inserts light children during the walk; see lib/jsdom/living/helpers/dom-tree.js:109-137.

Range operations now share one helper. Comparing two positions and finding a range's container both need the common ancestor of two nodes and that ancestor's child on each path, and commonAncestorInfo() returns all three in one walk; Range-impl.js uses it, as at lib/jsdom/living/range/Range-impl.js:201. The commit message lists fixes that came with the rewrite:

  • A CDATA section has the length of its text, because CharacterDataImpl overrides the new _length getter; before, range boundaries counted its children and saw zero. See lib/jsdom/living/nodes/CharacterData-impl.js:28-30.
  • normalize() merges only descendant text nodes, so calling it on a text node no longer removes the node or merges its siblings. See lib/jsdom/living/nodes/Node-impl.js:503.

Two smaller fixes sit in this theme. NodeIterator follows the latest version of its standard, per commit abaedd23, and the release notes say a filter that removes nodes no longer breaks its traversal. HTML serialization treats a CDATA section as text, so one adopted into an HTML document serializes as text. The other files swap a domSymbolTree call for the matching node method, such as domSymbolTree.childrenToArray(node) for node._childrenToArray().

_insert() runs post-connection steps after every node is in

Commit 94301581 brings _insert() to the standard's phases, in this order:

  1. 1Take a fragment's children out of the fragment, and queue the record a MutationObserver on the fragment receives.
  2. 2Shift live ranges that sit after the insertion point.
  3. 3For each node, in the per-node loop: adopt it, link it, clear caches, add it to the document's id and name caches, and run insertion steps and custom element callbacks on it and every descendant, including inside shadow trees.
  4. 4Queue the parent's mutation record, then run the parent's children inserted steps.
  5. 5Collect every descendant that has post-connection steps, then run them for each one still connected.

The call to the children inserted steps and the last phase are new:

lib/jsdom/living/nodes/Node-impl.js:1084-1105

    if (!suppressObservers) {
      queueTreeMutationRecord(this, nodesImpl, [], previousChildImpl, childImpl);
    }

    this._childrenInsertedSteps();

    for (const node of nodesImpl) {
      for (const inclusiveDescendant of node._shadowIncludingInclusiveDescendants()) {
        if (inclusiveDescendant._postConnectionSteps) {
          postConnectionNodes ||= [];
          postConnectionNodes.push(inclusiveDescendant);
        }
      }
    }

    if (postConnectionNodes) {
      for (const node of postConnectionNodes) {
        if (node.isConnected) {
          node._postConnectionSteps();
        }
      }
    }

_insert() now collects every node before it runs any post-connection step, as the standard does, so a script that inserts or removes nodes cannot change which nodes get those steps. The if (node.isConnected) test is the standard's own condition, and it skips a node that an earlier step disconnected. A hook appears only on classes that need it, and _insert() tests for its presence, as the comment at lib/jsdom/living/nodes/Node-impl.js:468-471 explains.

HTMLScriptElement uses both new hooks. Its _postConnectionSteps() prepares the script; see lib/jsdom/living/nodes/HTMLScriptElement-impl.js:41-48. Its children inserted steps, added by commit 4f374b99, cover a connected script that starts empty and then receives text:

lib/jsdom/living/nodes/HTMLScriptElement-impl.js:50-62

  // https://html.spec.whatwg.org/multipage/scripting.html#script-processing-model, moved from the
  // children changed steps to the children inserted steps in
  // https://github.com/whatwg/html/pull/12282. Being inserted-only is what keeps a removal or a
  // character data change from running the script.
  _childrenInsertedSteps() {
    super._childrenInsertedSteps();

    if (!this.isConnected) {
      return;
    }

    this._postConnectionSteps();
  }

The comment links the HTML change behind this and says that running only on insertion is what keeps a removal, or an edit to the script's text, from running the script.

The rest of this theme renames hooks and makes the fixes below, according to commit af483ae2 and its neighbors. The element classes replace _attach() and _detach() with the standard's insertion steps and removing steps. They replace _attrModified() with attribute change steps, which now receive the attribute's namespace and run after the attribute's value is stored. The HTML parser's path for inserting text before a node now calls _insert() with that reference node, and the XML parser prepares a script once its contents are parsed.

  • replaceChildren() checks validity while ignoring the children it is about to remove. So document.replaceChildren(document.createElement("html")) on a document that already has a root element no longer throws; see lib/jsdom/living/nodes/ParentNode-impl.js:55.
  • Removing a focused element, or its ancestor, moves focus back to the document, including inside shadow trees.
  • Radio groups are defined by tree, form owner, and a non-empty name.
  • A canceled click restores the previous radio only if it is still in the group.
  • A <select> updates its selection when an option's nearest select changes, and stops resetting it when unrelated descendants change.
  • Cloning appends each clone before cloning its children, and a cloned <input> keeps indeterminate.
  • Adding or changing a connected script's src goes through script preparation, so a non-JavaScript or already-started script does not run.
  • A script honors its type attribute and the legacy for and event attributes, and document.currentScript survives nested scripts.
  • Frames connect at the same point as iframes.
  • Stylesheet loading and frame source updates use isConnected, and removing a shadow host unregisters the stylesheets in its shadow tree.
  • node.lookupNamespaceURI() returns the fixed namespaces for the xml and xmlns prefixes.
  • element.translate handles an empty attribute and a missing parent.

One memoized-query object per node, and collections that refresh on read

Every insertion and removal calls _invalidateCaches() on the parent:

lib/jsdom/living/nodes/Node-impl.js:452-465

  // Call this before running element-specific steps, so collection and style reads reflect the mutation.
  _invalidateCaches() {
    this._version++;
    this.#memoizedQueries = null;
    for (let ancestor = this; ancestor !== null; ancestor = ancestor.parentNode) {
      ancestor._version++;
      ancestor.#memoizedQueries = null;
    }

    this._childrenList?._invalidate();
    this._childNodesList?._invalidate();
    if (this.isConnected) {
      this._ownerDocument._clearStyleCache();
    }

The new _invalidate() only empties the stored list. The collection rebuilds when read, if its owner node's _version has moved past the one it last saw:

lib/jsdom/living/nodes/HTMLCollection-impl.js:43-56

  _invalidate() {

  _update() {
    if (this._version < this._element._version) {
      const snapshot = this._query();
      for (let i = 0; i < snapshot.length; i++) {
        this._list[i] = snapshot[i];

      this._list.length = snapshot.length;

Named properties on document and window

document.myForm is new in this release, from commit 5f951834. Document.webidl enables the named getter, and DocumentImpl answers it. The elements that can contribute are embed, form, iframe, img, and object; see lib/jsdom/living/nodes/Document-impl.js:86. A private map holds each name and its elements. Any insertion or removal in the document tree discards the map, and an attribute change discards it only when the change can alter the map. A lone iframe answers with its window; several matches answer with a collection:

lib/jsdom/living/nodes/Document-impl.js:738-750

    // Collections are per name and outlive the cache above, since the standard hands out the same
    // collection each time. The query reads the current map, so the collection stays live.
    this.#namedPropertyCollections ??= new WeakValueMap();
    let collection = this.#namedPropertyCollections.get(name);
    if (collection === undefined) {
      collection = HTMLCollection.createImpl(this._globalObject, [], {
        element: this,
        query: () => this.#namedPropertyElements.get(name) ?? []
      });
      this.#namedPropertyCollections.set(name, collection);
    }

    return collection;

The standard requires the same collection object each time, so the collection must outlive the map, which is rebuilt after mutations. WeakValueMap, new in helpers/weak-value-map.js, holds each collection through a WeakRef, and a FinalizationRegistry removes the entry after the collection is reclaimed. A script that keeps the collection gets the same object back, and an unused one can be garbage-collected.

window named properties already existed, and commit ef956205 and its neighbors fix them in three ways:

  • Elements count only when they belong to the window's own document, so elements in a DOMParser document no longer appear on window. The test is inAssociatedDocument(); see lib/jsdom/living/window-properties.js:13-16.
  • The tracker that maps each name to its elements is created with the first contributing element and deleted with the last, so a window with no named elements holds none; see lib/jsdom/living/window-properties.js:149-151.
  • Empty and namespaced id and name attributes no longer count.

  _queueATask(steps, { signal } = {}) {
    return new Promise((resolve, reject) => {
      setImmediate(() => {
        if (this._isDestroyed || signal?.aborted) {
          resolve();
          return;
        }
        try {
          resolve(steps());
        } catch (error) {
          reject(error);
        }
      });
    });

The helper checks _isDestroyed when the task runs, not when it is queued, so a task queued just before close() is dropped too. The optional signal lets navigation tasks be canceled without touching unrelated tasks. The promise settles either way, which lets a caller clean up in finally.

Other entry points check _isDestroyed directly. New timers return 0, as at lib/jsdom/browser/Window.js:538-540, and the resource loader stops starting subresource loads. The commit message says jsdom still does not suspend and resume inactive documents, and does not model task sources, the standard's grouping of tasks by kind.

Quiz

A script appends a through f to an <ol>, removes f, and then a live range needs d's index. What does treeIndex() do?

Removing the last child moves no other child, so remove() marks the cache stale only when the removed node had a next sibling. f had none, so cachedChildren stays null and treeIndex() returns the cachedIndex d got at append time. A walk from a, partial or full, happens only after a middle insertion or removal. A backward count is what a tree without stored indexes has to do.

A script holds ul.children for a list in the body, and an ordered XPath iterator result over the document. It then appends a text node to a <footer> elsewhere in the body. What happens to each on its next use?

_invalidateCaches() runs on the footer and bumps _version on the footer and each of its ancestors, up to the document. The XPath result compares the document's version, so it turns invalid whatever kind of node was added. The list is not an ancestor of the footer, so its version and its children collection stay as they were, and the next read rebuilds nothing. No node outside that ancestor chain is touched.

document named properties come from a map built on the first lookup and discarded by any insertion or removal in the document tree. For which page would building the answer fresh on every lookup do better?

Building the map scans the whole document, while a fresh answer could stop at the elements for one name. When almost every lookup follows a mutation, each map is built for one read and then thrown away, so the cache adds work. A loop with no mutations is the case the cache is for. A single read at load costs one scan either way, and a shared name changes what the answer is, not how often the map is rebuilt.

A script sets audio.volume = 0.5 and, in the same turn, calls window.stop() instead of window.close(). Does volumechange fire?

The setter queues the event through _queueATask() with no signal, so the task is dropped only if _isDestroyed is set when it runs. Only window.close() sets that flag; window.stop() closes the request manager and leaves queued tasks alone. The event fired synchronously in 30.0.1, but now it is queued, and the setter does not look at the element's source at all.

The observer's node list, the map of named-property collections, and the abort algorithm kept on each listener record all fix memory leaks. What principle do the three share?

Each structure exists so jsdom can find an object later: the nodes to unregister from, the collection to hand back, the listener to remove on abort. Each one kept that object, or its callback, alive longer than the page did. Weak references fix the observer list and the collection map, and removing the abort algorithm with its listener fixes the signal. Discarding stale caches and allocating on first use are real ideas in this release, but neither one releases memory a page has stopped using.
