FastAPI PR 15800: serving a frontend build with app.frontend()

The change adds app.frontend() and router.frontend(), which serve a frontend build directory only after every path operation has missed, and answer a missing path with the build's 404.html or, for a browser navigation, its index.html.

fastapi/fastapi PR 15800 at 5bd3221f, explained 2026-11-16. References link to this commit.

Background

New to this area? Expand for the deeper background.

Every request reaches a FastAPI app as an ASGI scope. ASGI is the interface between Python web servers and async web apps, and the scope is a plain dict that holds the request's type ("http", "websocket", or "lifespan"), its method, its path, its root_path, and its headers. Routing code reads the scope to decide who answers. It also writes into the scope to pass facts to whoever answers.

Starlette, the toolkit FastAPI builds on, asks each route's matches(scope) for a Match and a child scope, a small dict of keys to merge into the scope if that route is chosen. Match.FULL means the path and the method both fit, Match.PARTIAL means only the path fits, and Match.NONE means the path does not fit. Starlette's Router.app (starlette/routing.py:662-710) walks its routes list in order and hands the request to the first FULL match. With none, it takes the first PARTIAL match, which usually answers 405 Method Not Allowed. With neither, it tries redirect_slashes: if the same path with its trailing slash added or removed would match a route, the answer is a 307 Temporary Redirect there. Otherwise it calls self.default, which under FastAPI raises a 404 that the app renders as {"detail":"Not Found"}.

A Mount hands every path under a prefix to another ASGI app, and moves that prefix into the scope's root_path so the inner app sees only the rest. A mount at / compiles to the pattern /{path:path} (starlette/routing.py:381), so it matches every path. Because the router takes the first FULL match in list order, the mount's position in routes decides whether it hides the routes after it.

StaticFiles is the Starlette app that serves a directory. Its get_path turns the request into a relative file path through get_route_path, a Starlette helper that returns scope["path"] with root_path removed. Its lookup_path joins that path to the directory and refuses any result outside it. With follow_symlink=False, the default, it resolves symlinks before comparing, so a link that points out of the directory is refused too. Its get_response serves a regular file through file_response. With html=True it does more. It redirects a directory URL to the same URL plus a trailing slash and then serves that directory's index.html, and it answers a request that finds no file with the top-level 404.html at status 404 (starlette/staticfiles.py:147-151). It never answers that request with index.html.

A single-page app ships one index.html plus scripts. The script reads the URL and draws the matching screen, so a URL such as /dashboard/settings is known only to the router inside the browser, and no file has that name. When a user reloads that URL or opens it from a bookmark, a deep link, the server has to answer with index.html so the script can start. The new tutorial calls this client-side routing. Static-site tools such as Astro write one HTML file per page instead, and a URL with no file there should show the site's 404.html.

Browsers say what they want in the Accept header. A page navigation sends a list such as text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8. Each entry may carry a quality value q from 0 to 1, and q=0 means "not acceptable".

FastAPI's APIRouter subclasses Starlette's Router, and every FastAPI app keeps one as app.router (fastapi/applications.py:984). A path operation is FastAPI's name for an endpoint function bound to a path and a method, and its route object is an APIRoute. Before this change APIRouter did not override Router.app, so every request ran Starlette's order. The first route whose path and method fit (Match.FULL) answers; failing that, the first whose path fits (Match.PARTIAL, usually a 405); failing that, a 307 slash redirect; and last, self.default and its JSON 404.

include_router does not copy a child router's routes into the parent. It appends an _IncludedRouter (fastapi/routing.py:1518), a wrapper that holds the child router and the include's prefix, tags, and dependencies. When asked to match, the wrapper builds an _EffectiveRouteContext (fastapi/routing.py:1334) for each child route: a view of that route with the include's prefix and dependencies applied. effective_candidates() builds that list and caches it.

The root router matches and handles every request that goes through an include. For an included router, APIRouter.handle (fastapi/routing.py:2580-2588) sends the request to the include's selected route rather than to the child's own APIRouter.app, which runs only when the child is reached some other way, such as being mounted as an ASGI app. So the root router's APIRouter.app alone decides what happens when no route matches. FastAPI also keeps per-request facts of its own in a dict under scope["fastapi"], which _get_fastapi_scope creates on first use (fastapi/routing.py:841-844). The frontend code stores its path there.

The static files tutorial was the documented way to serve a directory: mount a StaticFiles app. For a frontend at /, Starlette leaves two gaps. The mount competes with path operations by its position in routes, and StaticFiles has no index.html answer for a deep link. The pull request states no motive. The tutorial page it adds states the goal: "FastAPI checks path operations first. The frontend files are checked only if no normal route matched, so your API won't be affected" (docs/en/docs/tutorial/frontend.md:17). That the two gaps prompted the change is my reading of the code. A frontend enters the code at APIRouter.frontend, and a request enters at APIRouter.app.

Key concept A low-priority route is one the root router tries only after every ordinary route, every partial match, and the slash redirect have failed. The change adds this low-priority tier as APIRouter._low_priority_routes and puts only frontends in it.

Intuition

Picture the root router as two tiers. The first is routes: the path operations and the included routers, matched exactly as Starlette matches them. The second is the low-priority tier, which holds only frontends. A frontend is asked only once the first tier has failed completely, partial matches and the slash redirect included. So a frontend at / can claim every path without hiding a path operation, whether app.frontend() runs before or after the @app.get decorators.

The order APIRouter.app tries things in

  1. 1routes, first Match.FULL: that route answers
  2. 2routes, first Match.PARTIAL: usually a 405
  3. 3redirect_slashes: a 307 when the flipped slash matches a route
  4. 4the low-priority tier, through _match_low_priority: new
  5. 5self.default: the JSON 404

Inside the low-priority tier, three new classes share the work. _FrontendStaticFiles is the StaticFiles subclass that answers for one directory. _FrontendRoute is one frontend() call: a path prefix such as /app and its _FrontendStaticFiles. _FrontendRouteGroup holds every _FrontendRoute one router registered, so they can be compared by prefix. A route cuts its prefix off the request path and stores the remainder under scope["fastapi"]["frontend_path"], where _FrontendStaticFiles looks it up. In the code, APIRouter.app reaches the tier through _match_low_priority, which walks what _iter_low_priority_routes yields.

When the lookup finds no file, the fallback argument decides. It takes "auto", the default, or "index.html", "404.html", or None. "404.html" serves that file with status 404. "index.html" serves the top-level index.html with status 200, but only to a request that looks like a browser navigation, which _is_frontend_navigation_request judges from the URL's last segment and the Accept header. "auto" tries 404.html first and index.html second, and uses whichever file exists. None gives the plain 404.

Take a single-page build in dist holding index.html, assets/app.js, and about/index.html, with no 404.html. It is served by app.frontend("/", directory="dist") beside one path operation, GET /api/users:

Requests against a single-page build with no 404.html
Request Accept What answers
GET /api/users text/html,… the path operation
GET /assets/app.js */* dist/assets/app.js, 200

The deep link and the missing script both find no file and send the same Accept list, so only the extension tells them apart. That keeps a missing script from arriving as an HTML page with status 200, which is my reading of why the navigation check exists. The tutorial says only that missing JavaScript, CSS, and images still return 404.

1. APIRouter.frontend adds the frontend to the low-priority tier

FastAPI.frontend passes its arguments straight to self.router.frontend (fastapi/applications.py:1288-1293), so an app and a router share one code path. APIRouter.frontend normalizes the path, creates the router's _FrontendRouteGroup on first use, and adds one _FrontendRoute to it:

fastapi/routing.py:2504-2514

normalized_path = _normalize_frontend_path(path)
if self._frontend_routes is None:
    self._frontend_routes = _FrontendRouteGroup()
    self._low_priority_routes.append(self._frontend_routes)
self._frontend_routes.add_frontend_route(
    _join_frontend_paths(self.prefix, normalized_path),
    directory=directory,
    fallback=fallback,
    check_dir=check_dir,
)
self._mark_routes_changed()

The group goes into _low_priority_routes and never into routes, which is what puts it in the low-priority tier. FastAPI.openapi builds the schema from routes (fastapi/applications.py:1095), so frontends stay out of it too (tests/test_frontend.py:739). Separately, _FrontendRoute.url_path_for raises NoMatchFound (fastapi/routing.py:1990-1991), so url_for, which builds a URL from a route name, cannot name a frontend.

_normalize_frontend_path (fastapi/routing.py:1773-1780) rejects an empty path, or one without a leading /, with an AssertionError, and strips a trailing slash from anything but /. _join_frontend_paths (fastapi/routing.py:1783-1788) prepends the router's own prefix, the one passed to APIRouter(prefix=...). A path of / becomes the prefix alone, and any other path is appended, so APIRouter(prefix="/internal").frontend("/ui", ...) registers /internal/ui.

Checks run when frontend() is called. _FrontendRoute.__init__ rejects any fallback outside the four values (fastapi/routing.py:1951-1954). For a missing directory, _FrontendStaticFiles.__init__ raises a RuntimeError that names the path as given and its resolved absolute form (fastapi/routing.py:1810-1814). The commit that added the absolute path gives the reason in its subject: "Make path errors show absolute path to help with debugging". An explicit fallback="index.html" or "404.html" also has its file checked (fastapi/routing.py:1821-1822). With check_dir=False neither check runs, and a missing directory fails on the first request instead, when StaticFiles checks its own directory. The constructor also hard-codes html=True and follow_symlink=False (fastapi/routing.py:1815-1820). A symlink in the build that points outside it is therefore refused, and frontend() has no argument to allow it.

2. APIRouter.app asks the low-priority tier last

APIRouter.app is new. Its first part (fastapi/routing.py:2516-2556) repeats Starlette's Router.app (starlette/routing.py:662-708), and comparing the two shows only cosmetic differences, such as a tuple in place of two variables. The one change of substance is this block, placed between the slash redirect and self.default, at step 4 of the order in Intuition:

fastapi/routing.py:2558-2578

(
    low_priority_match,
    low_priority_scope,
    low_priority_route,
    low_priority_context,
) = self._match_low_priority(scope)
if low_priority_match != Match.NONE and low_priority_route is not None:
    _update_scope(scope, low_priority_scope)

            low_priority_context

        original_route = low_priority_context.original_route
        if isinstance(original_route, APIRoute):

await self.default(scope, receive, send)

_match_low_priority returns the match, the child scope to merge, the route to call, and, for a route reached through an include, its _EffectiveRouteContext. Any result other than Match.NONE is used. A frontend gives Match.PARTIAL for methods other than GET and HEAD, so a POST still reaches the frontend, which answers 405.

The merge uses _update_scope (fastapi/routing.py:847-853) rather than scope.update. It copies top-level keys, but merges the child's scope["fastapi"] dict into the existing one instead of replacing it, so the remainder lands beside whatever FastAPI already stored there. The APIRoute branch serves no library code at this commit. Only tests put a path operation in the low-priority list, and the one that reaches this branch goes through an include (tests/test_frontend.py:174). The record does not say why the branch exists.

Tests pin down what this position means. A frontend in a router included before the router that holds GET /api/users still loses to that path operation (tests/test_frontend.py:513). And the slash redirect runs first, with a loop that reads only routes. With @app.get("/api/") and a build that holds api/index.html, a request for /api gets a 307 to the path operation at /api/ before the frontend is asked (tests/test_frontend.py:577).

3. Included routers add their frontends, prefixed

The low-priority tier also collects frontends registered on included routers. _iter_low_priority_routes yields the root router's own _low_priority_routes first, then asks each _IncludedRouter in routes, in inclusion order:

fastapi/routing.py:2600-2606

def _iter_low_priority_routes(
    self,
) -> Iterator[BaseRoute | _EffectiveRouteContext]:
    yield from self._low_priority_routes
    for route in self.routes:
        if isinstance(route, _IncludedRouter):
            yield from route.effective_low_priority_routes()

effective_low_priority_routes (fastapi/routing.py:1551-1571) mirrors effective_candidates() from Background. It wraps the child's own groups, recurses into the child's includes with the prefixes combined, and caches the result. The cache key is _get_routes_version(), which adds up the change counters of the child router and every router it includes. Each router bumps its own counter through _mark_routes_changed whenever its routes change, and frontend() bumps it too (fastapi/routing.py:2514). So the cache is rebuilt when a route is added to a child after include_router (tests/test_frontend.py:552). The wrapping is one new branch in _build_effective_context, the method that builds each _EffectiveRouteContext:

fastapi/routing.py:1581-1585

if isinstance(route, _FrontendRouteGroup):
    return _EffectiveRouteContext(
        original_route=route,
        starlette_route=route.with_prefix(self.include_context.prefix),
    )

with_prefix (fastapi/routing.py:2015-2021) copies the group and calls each route's with_path (fastapi/routing.py:1961-1964) with the include prefix joined on. with_path makes a shallow copy of the route, so the copy shares the original's _FrontendStaticFiles and no directory check runs twice.

Edge case A group is not an APIRoute, so its context carries none of the include's dependencies. A dependency passed to include_router(..., dependencies=[...]) or to FastAPI(dependencies=[...]) does not run for frontend requests, so an auth dependency there does not guard the build. Middleware still runs, because it wraps the whole router. No test covers this. On the head commit, a denying dependency on the include returns 403 for the router's path operation and 200 for its frontend.

_match_low_priority (fastapi/routing.py:2640-2645) walks those candidates, keeps the first FULL match it meets, and otherwise keeps the first PARTIAL. It compares no prefixes across groups. The prefix comparison happens only inside one group, in step 4.

4. A group picks its longest prefix and stores the remainder

_FrontendRouteGroup._match (fastapi/routing.py:2027-2048) asks each of its routes and keeps the most specific FULL match, scored by _frontend_path_specificity (fastapi/routing.py:1791-1794): / scores 0, and any other prefix scores its length in characters. A tie keeps the earlier route. So app.frontend("/", ...) and app.frontend("/admin", ...) on one router send /admin/settings to the admin build (tests/test_frontend.py:484). Each route's own check is _FrontendRoute.matches:

fastapi/routing.py:1966-1985

def matches(self, scope: Scope) -> tuple[Match, Scope]:
    if scope["type"] != "http":
        return Match.NONE, {}
    frontend_path = self._get_frontend_path(get_route_path(scope))
    if frontend_path is None:
        return Match.NONE, {}
    child_scope = {_FASTAPI_SCOPE_KEY: {_FASTAPI_FRONTEND_PATH_KEY: frontend_path}}
    if scope["method"] not in self.methods:
        return Match.PARTIAL, child_scope
    return Match.FULL, child_scope

def _get_frontend_path(self, route_path: str) -> str | None:
    if self.path == "/":
        return route_path.lstrip("/")
    if route_path == self.path:
        return ""
    prefix = self.path + "/"
    if route_path.startswith(prefix):
        return route_path[len(prefix) :]
    return None

The prefix check works on whole segments. A route at /app takes /app and /app/... but not /application (tests/test_frontend.py:473). The route reads the path through get_route_path, which strips a root_path that a proxy set (tests/test_frontend.py:598).

Unlike a Mount, the route leaves scope["path"] and root_path alone and puts the remainder in its child scope. _FrontendRouteGroup.handle (fastapi/routing.py:2050-2055) runs the match again, merges that child scope with _update_scope, and calls the route, which calls its _FrontendStaticFiles. There, the overridden get_path reads the remainder instead of the request path:

fastapi/routing.py:1837-1840

def get_path(self, scope: Scope) -> str:
    path = _get_fastapi_scope(scope).get(_FASTAPI_FRONTEND_PATH_KEY, "")
    assert isinstance(path, str)
    return os.path.normpath(os.path.join(*path.split("/")))

An exact prefix match leaves an empty remainder, which os.path.normpath turns into ".", the directory itself. So /app without a slash meets the directory branch in step 5 and, when the build has an index.html, gets a 307 to /app/.

5. _FrontendStaticFiles answers with a file, a redirect, a fallback, or a 404

_FrontendStaticFiles.get_response (fastapi/routing.py:1842-1883) keeps Starlette's opening. It refuses methods other than GET and HEAD with 405 and maps lookup errors as Starlette does (fastapi/routing.py:1846-1855): a PermissionError becomes 401, and a name that is too long or a ValueError becomes 404. A regular file goes out through the inherited file_response, and a directory holding index.html gets the same trailing-slash redirect Starlette gives. Like Starlette with html=True, it can serve 404.html at status 404, though through file_response, so a conditional request can get a 304 instead. The fallback modes and the index.html answer are new. The first rule that applies wins:

What get_response tries, in order

  1. 1a regular file: that file, 200
  2. 2a directory holding index.html: a 307 when the trailing slash is missing, otherwise that index.html
  3. 3fallback="404.html", or auto with a 404.html: that file, 404
  4. 4fallback="index.html", or auto with an index.html, on a browser navigation: the top-level index.html, 200
  5. 5anything else: HTTPException, the JSON 404

fastapi/routing.py:1872-1883

The 404.html branch comes first and has no navigation check. The index.html branch serves the top-level index.html with status 200, and only when _is_frontend_navigation_request agrees. Both end in _fallback_response (fastapi/routing.py:1889-1901), which raises a RuntimeError when an explicit fallback file has gone missing and otherwise serves the file through file_response with the chosen status. The navigation check:

fastapi/routing.py:1921-1939

def _is_frontend_navigation_request(scope: Scope) -> bool:
    route_path = get_route_path(scope)
    final_segment = route_path.rsplit("/", 1)[-1]
    if os.path.splitext(final_segment)[1]:
        return False
    request = Request(scope)
    wildcard_accepted = False
    html_rejected = False
    for media_type, quality in _iter_accept_media_types(
        request.headers.get("accept", "")
    ):
        if media_type in {"text/html", "application/xhtml+xml"}:
            if quality == 0:
                html_rejected = True
            else:
                return True
        elif media_type == "*/*" and quality != 0:
            wildcard_accepted = True
    return wildcard_accepted and not html_rejected

The URL's last segment decides first: if os.path.splitext finds an extension, the request is for a file and the answer is no. Otherwise the Accept entries decide, as _iter_accept_media_types (fastapi/routing.py:1904-1918) parses them, reading a q it cannot parse as 1.0. An HTML type, text/html or application/xhtml+xml, with a nonzero q means yes. Failing that, */* with a nonzero q means yes, unless an HTML type appeared with q=0. Anything else, application/json or an empty header included, means no.

Edge case The extension check treats any dot after the first character of the last segment as an extension. A URL that only the browser-side router knows, such as /users/jane.doe, gets a 404 instead of the top-level index.html, even from a browser (tests/test_frontend.py:362).

Quiz

A React build in dist holds index.html and an assets/ folder, with no 404.html, and is served by app.frontend("/", directory="dist"). No path operation matches /reports/2026. A teammate runs curl http://localhost:8000/reports/2026, which sends Accept: */*. What comes back?

The last segment, 2026, has no extension, and a */* with a nonzero q counts as a navigation when no entry refused HTML. With no 404.html, auto mode falls back to the existing index.html at status 200, so curl gets the HTML page. The JSON 404 is what a client gets by sending Accept: application/json or an empty header. A 307 needs reports/2026 to be a directory holding its own index.html, and index.html is never served with status 404.

A Vue app with client-side routing works under app.frontend("/", directory="dist") with the default fallback: opening /dashboard/settings directly shows the app. Someone adds a branded 404.html to dist. What does a browser get now when it opens /dashboard/settings directly?

Auto mode checks for 404.html before it considers index.html, and the 404.html branch has no navigation check. Once the file exists, the deep link is just another path with no file, so it gets the branded page with status 404 and the router inside the page never loads. To keep client-side routing, pass fallback="index.html" and draw the not-found screen inside the app. The JSON 404 would need no usable fallback file, and a redirect would need a directory at that path.

An app serves its marketing site with app.frontend("/", directory="site"), and that build has a 404.html. An admin panel lives on a router, admin.frontend("/", directory="admin_dist"), included with app.include_router(admin, prefix="/admin"). No path operation matches /admin/users. Which build answers when a browser opens it?

The root router's own group comes first in _iter_low_priority_routes, and its / route gives a FULL match for every GET. _match_low_priority keeps the first FULL match it meets and drops later ones, so the included router's group never answers, and the site's lookup of admin/users misses into its 404.html. Longest-prefix choice happens only inside one group, which is why two frontend() calls on the same router would pick the admin build here. Call order does not matter, because the root's own list is always yielded first. No test in the pull request covers this mix; running the head commit gives the site's 404.html.

Suppose _FrontendStaticFiles dropped its get_path override and used the one it inherits from StaticFiles. A router serves dist with router.frontend("/", directory="dist") and is included with prefix="/app". The file dist/assets/app.js exists, and the build has no 404.html. What does GET /app/assets/app.js return?

The route never moves its prefix into root_path the way a Mount does. It leaves the remainder, assets/app.js, in scope["fastapi"]["frontend_path"]. The inherited get_path reads scope["path"] minus root_path, which is still /app/assets/app.js, so lookup_path looks for dist/app/assets/app.js and misses. The .js extension then rules out index.html, and with no 404.html the answer is the plain 404. Nothing on the path would redirect, because no directory was found.

Both app.frontend("/", directory="dist") and a Mount at / that holds a StaticFiles app can serve a build. In which situation would the plain mount still be the better fit?

StaticFiles accepts follow_symlink=True, which compares the joined path without resolving links, so a link out of the directory is served. _FrontendStaticFiles always passes follow_symlink=False, and frontend() has no argument to change it, so such a file gets a 404 (tests/test_frontend.py:676). Many path operations favor frontend(), which never competes with them. A proxy's root_path is honored by both. A 404.html for misses is something both serve as well.
