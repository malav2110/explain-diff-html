FastAPI PR 16102: check_dir="auto" for app.frontend()

The check_dir argument of app.frontend() and router.frontend() now defaults to "auto", which turns a missing frontend folder into a warning when FASTAPI_ENV is "development", the value fastapi dev sets, and keeps the error at app creation for any other FASTAPI_ENV value, or none.

Background

New to this area? Expand for the deeper background.

FastAPI added app.frontend() in PR 15800. It serves the static files a frontend build tool writes into a folder, usually dist, from inside the FastAPI app. The files sit on low-priority routes: FastAPI path operations match first, and a request reaches the files only when no path operation matched. router.frontend() does the same on an APIRouter.

fastapi dev and fastapi run are commands from the separate fastapi-cli package, which the fastapi[standard] extra installs. fastapi dev starts a reloading server for local work, and fastapi run starts one for production. Both import your module, so a module-level call such as app.frontend("/", directory="dist") runs once while the app is created, before any request arrives. An extra is a named group of optional dependencies, such as standard.

An environment variable is a named string a process receives when it starts. Python reads them through os.environ, and child processes inherit them. os.environ.setdefault(name, value) writes the value only when the name is absent.

warnings.warn(message) reports a problem without stopping the program. With no category it emits a UserWarning, which Python's default filters print to standard error with a file name and line number. Each function call still running is a frame on the call stack, and the stacklevel argument picks whose file and line the warning reports: 1 is the line that calls warnings.warn, 2 is the line that called the function holding it, and 3 goes one caller further up.

Before this change, check_dir was a bool that defaulted to True on both public methods: FastAPI.frontend, the method app.frontend() calls, and APIRouter.frontend, the method router.frontend() calls. Each parameter is declared as Annotated[type, Doc(...)], which attaches its documentation to its type. The value travels this chain, in order:

  1. FastAPI.frontend passes it to its router's APIRouter.frontend.
  2. APIRouter.frontend hands it to _FrontendRouteGroup.add_frontend_route, which collects the router's frontend routes.
  3. add_frontend_route builds a _FrontendRoute, the route object that matches paths.
  4. _FrontendRoute builds a _FrontendStaticFiles, FastAPI's subclass of Starlette's StaticFiles, which serves the files.

_FrontendStaticFiles.__init__ is where the value is used. When check_dir is true and the folder is missing, it raises RuntimeError with the folder name and its absolute path, which _get_resolved_absolute_path computes. The fallback argument names the file served for a path with no matching file. When check_dir is true and fallback is "index.html" or "404.html", _check_fallback_file also confirms that file exists. Starlette's StaticFiles constructor runs its own folder check when it gets a true check_dir. With check_dir=False, all three checks are skipped, and Starlette's check_config runs on the first request instead, raising if the folder is still missing.

So the old default made a missing dist fatal at app creation. The pull request body names the case: "Frontend build output might not exist yet when starting the backend during development." check_dir=False avoided the crash, but it also dropped the error at app creation in production, where the body says missing files should keep "failing early".

The change adds one input, the FASTAPI_ENV environment variable. No code in the fastapi package reads it at the pull request's base commit, 628663f. fastapi-cli 0.0.32 sets it inside fastapi dev with os.environ.setdefault("FASTAPI_ENV", "development"), at src/fastapi_cli/cli.py:402 in that release. fastapi-cli PR 477 added that line, and it is the only place the CLI sets the variable, so fastapi run leaves it unset. fastapi dev is where the flow map at the top of the Code section starts: it sets the variable, then imports the module that calls app.frontend().

Key concept A frontend folder can be checked at two moments: at app creation, when app.frontend() runs during import, or at the first request, when Starlette's check_config runs. check_dir=True picks app creation and check_dir=False picks the first request. The new "auto" value picks one of those two moments when app.frontend() runs.

Intuition

"auto" is a question FastAPI answers when app.frontend() runs: is this a development process? A helper named _resolve_frontend_check_dir asks it. If FASTAPI_ENV is exactly "development", the answer becomes check_dir=False, with a warning when the folder is missing. Any other value, or no value, becomes check_dir=True, which this page calls the strict branch. From there on, only code that already existed runs.

Take a main.py that calls app.frontend("/", directory="dist"), in a project where no dist folder exists yet:

What happens when the app is created, with no dist folder and nothing exported unless the row says so
Started with FASTAPI_ENV At app creation
fastapi dev "development", set by the command Warning, and the server starts
fastapi run unset RuntimeError
uvicorn main:app "staging", exported by hand RuntimeError
fastapi dev, with check_dir=True "development", set by the command RuntimeError

In development the folder check moves to request time. Starlette sets its config_checked flag only after check_config passes, at starlette/staticfiles.py:93-95 in Starlette 1.3.1, the version the repository's lock file, uv.lock, pins. So within one process, a request that fails before the frontend build runs does not block requests made after the build writes dist:

  1. 1fastapi dev sets FASTAPI_ENV=development, then imports main.py
  2. 2app.frontend("/", directory="dist") warns that dist does not exist, and the server starts
  3. 3GET / gets a 500: check_config finds no dist, so config_checked stays false
  4. 4The frontend build writes dist/index.html
  5. 5GET / gets a 200: check_config passes and the file is served

Code walkthrough

Flow: fastapi dev sets FASTAPI_ENV → app.frontend() or router.frontend() accepts "auto" → _resolve_frontend_check_dir turns it into a bool → _FrontendStaticFiles raises at app creation or leaves the check to the first request.

Both public methods accept "auto" and default to it

FastAPI.frontend and APIRouter.frontend declare check_dir with the same annotation and the same docstring. The type widens from bool to bool | Literal["auto"], and the default changes from True to "auto". Literal["auto"] is a typing form that admits exactly the string "auto", so a type checker still rejects check_dir="yes".

A caller who already passes check_dir=True or check_dir=False keeps the old behavior, because the helper in the next step returns both unchanged. Only callers who relied on the default see a difference, and only when FASTAPI_ENV is "development".

_resolve_frontend_check_dir turns "auto" into a bool

The new helper sits in fastapi/routing.py, and both public methods call it. It takes the folder and the raw argument, and it always returns a plain bool.

fastapi/routing.py:1880-1895 

def _resolve_frontend_check_dir(
    *,
    directory: str | os.PathLike[str],
    check_dir: bool | Literal["auto"],
) -> bool:
    if check_dir != "auto":
        return check_dir
    if os.environ.get("FASTAPI_ENV") != "development":
        return True
    if not os.path.isdir(directory):
        warnings.warn(
            f"Frontend directory '{directory}' does not exist. "
            f"Resolved absolute path: '{_get_resolved_absolute_path(directory)}'",
            stacklevel=3,
        )
    return False

The three if statements run in order:

  • Any value other than "auto" goes straight back. That is the pass-through for explicit True and False.
  • Outside development the answer is True, the strict branch. os.environ.get returns None for an unset variable, and None is not "development", so an unset variable lands here too.
  • In development, the helper warns if the folder is missing and then returns False. The return False sits outside the if, so in development the answer is False whether or not the folder exists. The warning is then the only signal at app creation, and it covers only a missing folder.

The warning text repeats the RuntimeError message that _FrontendStaticFiles raises at fastapi/routing.py:1909-1910, so the same folder name and absolute path appear whichever branch runs.

Edge case The comparison is != against the exact string "development". A hand-set Development, dev, or development with a trailing space takes the strict branch, and the app raises at app creation when the folder is missing.

pyproject.toml raises the fastapi-cli minimum version in three extras, so installing fastapi[standard] brings a CLI that sets the value. At pyproject.toml:61, pyproject.toml:80, and pyproject.toml:98, the standard, standard-no-fastapi-cloud-cli, and all extras move from >=0.0.8 to >=0.0.32. The fastapi-cli 0.0.32 release is the one that sets FASTAPI_ENV. With an older CLI, the variable stays unset, and "auto" takes the strict branch even under fastapi dev.

The double call keeps the warning's location in user code. That looks like the reason the helper runs in both methods rather than only in the router, though the code does not say so; the tests below show the location is intended. stacklevel=3 counts three frames up from the warnings.warn call. When main.py calls app.frontend(), the frames are:

  2. 2 fastapi/applications.py:1291 FastAPI.frontend calls the helper

Quiz

A project moves its frontend setup into a helper in ui.py: def mount_ui(app): app.frontend("/", directory="dist"). Then main.py calls mount_ui(app). Under fastapi dev with no dist folder, which line does the warning name?

stacklevel=3 counts frames up from the warnings.warn call, not down from the program's entry point. Level 1 is the warn call, level 2 is FastAPI.frontend, and level 3 is whatever line called app.frontend(), which here sits inside mount_ui. The main.py line is one frame further up. A wrapper around the call moves the warning's location into the wrapper.

A developer's shell profile still exports FASTAPI_ENV=production from an old deploy script. They run fastapi dev before the frontend has ever been built. What happens?

fastapi dev uses os.environ.setdefault, which writes "development" only when FASTAPI_ENV is absent. The exported "production" survives, the helper takes its strict branch and returns True, and _FrontendStaticFiles raises while the module imports. Unsetting the variable restores the warning.

Under fastapi dev, a project calls app.frontend("/", directory="dist", fallback="index.html"). The dist folder exists, but the build has not written index.html into it yet. What happens when the app is created?

In development the helper returns False whether or not the folder exists, and it warns only about a missing folder, so this run prints nothing. With check_dir false, _FrontendStaticFiles also skips _check_fallback_file, so the missing index.html surfaces later, as a RuntimeError when a browser navigation needs the fallback. Once the build writes the file, the same process serves it. Under fastapi run the same call raises at app creation.

The "auto" default covers the situation fastapi dev creates. When is an explicit check_dir=False still the better choice?

Outside development, "auto" means the strict check, so a process that only gets its files after import would crash at app creation. check_dir=False moves that process's check to request time, whatever FASTAPI_ENV says. The fastapi dev session is the case "auto" already handles, and the image and the CI job both want the error at app creation that "auto" keeps.

The change keeps the import-time error everywhere except a process marked as development, where it warns and leaves the check to request time. Which principle is that an instance of?

The strict branch stays the default for every process not marked as development, because there a missing build means something shipped without its files. Lazy initialization and graceful degradation each describe the development branch alone; under fastapi run the app still fails at creation. Convention over configuration is about inferring the folder, and the change never touches directory.
