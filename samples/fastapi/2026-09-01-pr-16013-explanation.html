Thread-safe route building in included routers

Each included router now rebuilds its cached route lists under its own lock and publishes each list only when it is complete, so threads that share one app can no longer read a half-built list or append into the same one.

fastapi/fastapi PR 16013 at 9f919ff, explained 2026-11-16. References link to this commit.

Background

New to this area? Expand for the deeper background.

CPython, the standard Python interpreter, runs one thread at a time under its global interpreter lock (GIL), and it can switch threads between any two bytecode steps. So a single assignment such as self.items = new_list lands as one step that another thread sees whole. A loop that appends ten items is ten steps, and another thread can run, and read the half-filled list, between any two of them. Free-threaded CPython removes the GIL, so its threads really do run at the same moment.

A check-then-act race happens when a thread checks a condition, acts on it, and another thread changes the condition in between. A threading.Lock prevents that by admitting one thread at a time: code inside with lock: runs only while the thread holds the lock, and any other thread reaching that line waits for the release. The lock is not reentrant. A thread that already holds it and asks again waits forever, on itself.

A dataclass declares its attributes as fields. field(default_factory=threading.Lock) calls threading.Lock() once per new instance, so no two instances share the object. repr=False and compare=False leave a field out of the __repr__ and __eq__ methods the dataclass writes.

The tests use three helpers. threading.Barrier(n) holds threads until n of them arrive, then releases them together. threading.Event lets one thread wait until another calls set(). pytest's monkeypatch.setattr replaces an attribute for one test.

Discussion 15914 reported that an app's first requests could go wrong when several threads sent them at once. The setup was a test suite in which each thread creates its own TestClient, Starlette's test client, against one shared app. Each client runs the app on its own event loop in its own thread. A valid route could answer 404. The route list FastAPI caches for an included router could keep duplicate entries for the life of the app: 283 entries for 120 routes in one of the reporter's runs. The global warnings.filters list could gain stray entries. The reporter noted that a server running one event loop matches every request on one thread, so it is not exposed. The reply that links this pull request calls the issue "mostly harmless", since it would mainly apply to parallel test runs that use threads, and says the fix shipped in FastAPI 0.139.2.

The race lives in _IncludedRouter, a dataclass this page calls the wrapper. include_router(router) appends one wrapper to the parent's routes (fastapi/routing.py:3260-3262). The wrapper holds original_router, the router that was included, and include_context, a _RouterIncludeContext with the prefix, tags, dependencies, and other settings the include adds. According to the discussion, the wrapper arrived in FastAPI 0.137.0 with pull request 15745, a refactor of the router internals.

The wrapper builds the routes it serves on demand, in two lists. effective_candidates() returns one entry for each route of original_router that it knows how to serve. Each route that is not itself an included router becomes an _EffectiveRouteContext, the route with the include context applied, built by _build_effective_context() (fastapi/routing.py:1639). For an API route, that means compiling the prefixed path into a regex, creating the response model fields, and building the dependency tree in _populate_api_route_state() (fastapi/routing.py:947). A router included inside the included router becomes a child wrapper, child_branch in the code, whose context is the two include contexts joined by combine(). The second list, from effective_low_priority_routes(), holds routes tried only after every regular route has failed to match. Those are the routes that APIRouter.frontend() registers to serve a built frontend from a directory, kept in _low_priority_routes (fastapi/routing.py:2661).

Each list is cached on the wrapper beside a version stamp: _effective_candidates with _effective_candidates_version, and _effective_low_priority_routes with _effective_low_priority_routes_version. Both stamps start as None. Every APIRouter keeps an integer, _routes_version, and _mark_routes_changed() (fastapi/routing.py:2527-2528) adds one to it each time a route or a router is added. _get_routes_version() (fastapi/routing.py:2530) returns that integer plus the integers of every router included below. Each method compares the version that call returns with its stamp, returns the cached list on a match, and rebuilds on a mismatch. A stamp of None never matches, so the first request through a wrapper does the build.

The app's top-level APIRouter asks each route whether it matches, in its app method (fastapi/routing.py:2670). For a wrapper, that question ends in the wrapper's _match() (fastapi/routing.py:1714), which loops over effective_candidates() (fastapi/routing.py:1718) and returns the first full match. When no route matches and no slash-toggled redirect does either (fastapi/routing.py:2697), app calls _match_low_priority() (fastapi/routing.py:2717), which reaches effective_low_priority_routes() through _iter_low_priority_routes() (fastapi/routing.py:2760). When that fails too, self.default (fastapi/routing.py:2732) answers 404.

Intuition

A version stamp makes a promise: when it matches, the list beside it is complete and current. The old rebuild broke that promise for a moment. These lines, from the diff, did it:

fastapi/routing.py before the change, from the diff

self._effective_candidates = []
candidates = self.original_router.routes
for route in candidates:
    # elided: the loop body, which appends one entry per route
    # to self._effective_candidates
self._effective_candidates_version = routes_version
return self._effective_candidates

Take a router with three routes, /a, /b, and /c, included once, and three threads sending the app's first requests. Thread A reads the stamp, sees None, and the interpreter pauses it just before the reset line, self._effective_candidates = []. Thread B reads None too, builds the full list, and stamps it 3, the router's version after its three routes were added. Then A wakes up and runs its next line.

A's reset puts an empty list on the wrapper while B's stamp still says 3. Thread C asks for /c, finds the stamp current, loops over the empty list, matches nothing, and gets a 404 for a route that exists. This is a check-then-act race: A acted on a check that B had made stale. Once A finishes its loop the list is whole again, so this failure is brief and depends on timing. A different overlap leaves extra entries in the list, and because the stamp then matches, they stay until a route is added. That is the duplication the discussion measured.

The fix changes who builds and where. Only one thread builds at a time, and it builds where nobody else can look: in a local list, which other threads see only when one assignment puts the finished list on the wrapper. This page calls that assignment publishing. That assignment comes before the stamp, so a thread that sees the new stamp also sees the new list. A thread that had to wait for the builder checks the stamp again once it holds the lock, finds it current, and takes the list the builder made.

Key concept This pattern is double-checked locking: check without the lock, take the lock, then check again. The rest of this page calls the two checks the check before the lock and the check inside the lock.

Code walkthrough

Flow: include_router creates a wrapper with its own lock → a request reaches _match() → effective_candidates() checks, locks, checks again, builds, and publishes → an unmatched request reaches effective_low_priority_routes(), which repeats the pattern under the same lock.

Each wrapper gets its own lock

fastapi/routing.py now imports threading (fastapi/routing.py:10) and gives the wrapper dataclass one new field:

fastapi/routing.py:1572-1577 

class _IncludedRouter(BaseRoute):
    original_router: "APIRouter"
    include_context: _RouterIncludeContext
    _effective_routes_lock: Any = field(
        default_factory=threading.Lock, repr=False, compare=False
    )

Because the field uses default_factory, every wrapper gets a fresh lock. That covers the wrapper include_router creates and every child_branch the two methods create. repr=False and compare=False leave the lock out of the wrapper's __repr__ and __eq__.

effective_candidates() checks, locks, checks again, then publishes

fastapi/routing.py:1587-1610 

def effective_candidates(self) -> list["_EffectiveRouteContext | _IncludedRouter"]:
    routes_version = self.original_router._get_routes_version()
    if routes_version == self._effective_candidates_version:
        return self._effective_candidates
    with self._effective_routes_lock:
        routes_version = self.original_router._get_routes_version()
        if routes_version == self._effective_candidates_version:
            return self._effective_candidates
        effective_candidates: list[_EffectiveRouteContext | _IncludedRouter] = []
        for route in self.original_router.routes:
            if isinstance(route, _IncludedRouter):
                child_context = self.include_context.combine(route.include_context)
                child_branch = _IncludedRouter(
                    original_router=route.original_router,
                    include_context=child_context,
                )
                effective_candidates.append(child_branch)
                continue
            route_context = self._build_effective_context(route)
            if route_context is not None:
                effective_candidates.append(route_context)
        self._effective_candidates = effective_candidates
        self._effective_candidates_version = routes_version
        return effective_candidates

The first four lines are unchanged. When the stamp matches, the method returns the cached list before it reaches the lock, so a wrapper whose list is built serves requests the way it did before.

On a mismatch, the thread enters with self._effective_routes_lock: (fastapi/routing.py:1591), and only one thread per wrapper gets past that line at a time. The check inside the lock (fastapi/routing.py:1592-1594) calls _get_routes_version() afresh and compares again. A thread that waited while another built finds the stamp current here and returns the list the other thread published.

The build appends to a local variable, also named effective_candidates (fastapi/routing.py:1595), instead of to self._effective_candidates. The loop body is the old one, indented under the with, and it walks self.original_router.routes directly instead of through the old candidates name. No other thread can reach the local list while it fills.

The last three lines publish it (fastapi/routing.py:1608-1610). The list goes onto the wrapper first and the stamp second. The order matters because the check before the lock reads both attributes with no lock held, so a thread that sees the new stamp also sees the new list.

The first new test, test_included_router_candidate_cache_is_thread_safe (tests/test_router_include_context.py:903), uses the sizes from the discussion's reproduction: 120 routes and six threads. A threading.Barrier (tests/test_router_include_context.py:916) releases the six threads together, and each calls effective_candidates() on the unbuilt wrapper. The test asserts that all six got the same list object (tests/test_router_include_context.py:930), that it holds 120 entries (tests/test_router_include_context.py:931), and that a request for /items/0 still answers.

effective_low_priority_routes() repeats the pattern under the same lock

The second method gets the same moves: the unchanged check before the lock (fastapi/routing.py:1613-1615), the lock (fastapi/routing.py:1616), the check inside it (fastapi/routing.py:1617-1619), and a local list (fastapi/routing.py:1620). It takes the same _effective_routes_lock as effective_candidates(), so one wrapper never builds both of its lists at the same moment. Its ending differs, because it folds nested routers in as it goes:

for route in self.original_router.routes:

        child_context = self.include_context.combine(route.include_context)

            original_router=route.original_router,

self._effective_low_priority_routes = effective_low_priority_routes
self._effective_low_priority_routes_version = routes_version
return effective_low_priority_routes

For each router included inside original_router, the method makes a child_branch and calls the child's effective_low_priority_routes() while it still holds its own lock. The child is a new wrapper with a new lock of its own, from the dataclass field, so that inner call checks and takes the child's lock, not the parent's. The parent copies the child's entries into its local list with extend and then drops the child. Publishing keeps the same order: list, then stamp.

Out of scope The lock keeps two threads from building one wrapper's lists at once. Two different wrappers can still build at the same moment. A build creates model fields for each API route, and each ModelField enters warnings.catch_warnings() (fastapi/_compat/v2.py:142), which saves and restores the process-wide warnings.filters. The discussion traces its third symptom, the stray filter entries, to those calls overlapping, and this change does not touch that code. The reply says that code "will be refactored either way".

The second new test, test_included_router_low_priority_cache_rechecks_version_after_lock (tests/test_router_include_context.py:935), aims at the check inside the lock. It includes an empty router and uses monkeypatch.setattr to replace that router's _get_routes_version() with a stub, get_routes_version (tests/test_router_include_context.py:943-945), which sets a threading.Event named version_checked and returns a fixed version. Then it runs this:

tests/test_router_include_context.py:953-958 

with included_router._effective_routes_lock:
    thread = threading.Thread(target=build_low_priority_routes)
    thread.start()
    assert version_checked.wait(timeout=1)
    included_router._effective_low_priority_routes_version = routes_version
thread.join()

The main thread holds the wrapper's lock, starts a thread that calls effective_low_priority_routes(), waits for version_checked, stamps the wrapper with the current version, and only then releases the lock. In that schedule the thread, once it holds the lock, finds the stamp current and returns from inside the with block. The final assertion, result == [[]] (tests/test_router_include_context.py:960), holds on either path. result collects the thread's return value, so [[]] means one empty list, and an empty router rebuilds to an empty list too. So what the test adds is a run through that return. That looks aimed at test coverage, which CI holds at 100% (.github/workflows/test.yml:242), though nothing in the record says so.

Quiz

Before this change, a router has three routes. Threads A and B both read the stamp as None. A resets the list, then B resets it, then both run their loops to the end. How many entries does _effective_candidates hold afterward?

The old loop called self._effective_candidates.append(), which looks the attribute up again on every call. After B's reset, that attribute names B's list, so both loops append there and the list A assigned is dropped empty. Which thread stamps last does not matter, because both write the same version. This is how the reporter's run ended with 283 entries for 120 routes, and why the merged code appends to a local variable.

Suppose _effective_routes_lock were one lock shared by every wrapper instead of one per instance. The app includes a router that itself includes another router. What happens to the first request that matches no regular route and falls through to the low-priority routes?

effective_low_priority_routes() creates each child_branch and calls the child's method while it still holds the parent's lock. With one lock per instance, that call takes the child's own lock. With one shared lock, the thread asks for a lock it already holds, and a threading.Lock is not reentrant, so the thread waits forever. The regular path escapes this, because effective_candidates() only creates the children; they build their own lists later, from _match(), after the parent has released the lock.

The discussion proposed building into a local list and publishing it, with no lock. Compared with that proposal, what does the merged version add?

Both versions publish only a finished list, so both close the empty-list window and the shared-append duplication, and in both a request on a built wrapper skips the lock. The lock and the check inside it add one thing: threads that arrive while the list is unbuilt wait, then take the builder's list, so the build runs once per wrapper instead of once per thread. The six-thread test checks that with result is results[0]. The reporter also noted that free-threaded Python builds may want the lock anyway.

In test_included_router_low_priority_cache_rechecks_version_after_lock, delete the line assert version_checked.wait(timeout=1) and keep everything else. What can now happen?

Without the wait, the main thread can stamp the wrapper before the new thread has read the version at all. The thread's check before the lock then matches, it returns at once, and the return inside the with block never runs. The test still passes, because the result is [[]] either way, so nothing reports the lost path. The stub sets version_checked from inside that check, so the wait holds the stamp back until the thread has started reading the version. The thread then nearly always reaches the lock first, though nothing strictly forces it.

The app runs under a server with one event loop, so every request is a coroutine on the same thread. Two requests arrive together at an app whose lists are unbuilt. What does the second request do when it reaches effective_candidates()?

Coroutines on one event loop switch only at an await. APIRouter.app reaches effective_candidates() through ordinary function calls, and the rebuild has no await inside, so the first request finishes the build and the stamp before the loop can run the second. The second request returns at the check before the lock and never touches it. That matches the discussion's note that a single-loop server does not contend on the rebuild.
