Falsy query errors now reach the error boundary from useQueries

This pull request makes useQueries and useSuspenseQueries throw a query's error to the nearest error boundary even when the queryFn rejected with a falsy value such as undefined, as useQuery already did.

TanStack/query PR 11305 at fc00bf4, explained 2026-11-15. References link to this commit.

Background

New to this area? Expand for the deeper background.

An error boundary is a React component that catches anything thrown while its children render, and shows a fallback in their place. JavaScript lets code throw any value, not only an Error, so throw undefined is legal. The tests in this pull request wrap each component in the ErrorBoundary component from the react-error-boundary package, with a fallback that renders the text "error boundary".

Suspense uses the same throw, with a promise as the value. A component that is not ready throws a promise while it renders. React shows the fallback of the nearest <Suspense> element, then renders the component again once that promise settles.

A falsy value is one that an if treats as false: undefined, null, '', 0, NaN, and false. Promise.reject() called with no argument rejects with undefined, so a query function written that way fails with no error value at all.

In TanStack Query, a query is a cached fetch named by its queryKey and run by its queryFn. The cache keeps one Query per key. Its state holds a status of 'pending', 'success', or 'error', along with data and error. A hook reads that state through an observer. The observer hands it a result object, typed QueryObserverResult, with fields such as isError, error, data, and isFetching.

Issue 11304 reports the bug: a query function that rejects with a falsy value reaches the error boundary from useQuery, but not from useQueries or useSuspenseQueries. Three hooks are involved:

  • useQuery watches one query by calling useBaseQuery, a shared implementation in packages/react-query/src/useBaseQuery.ts.
  • useQueries watches a list of queries through one QueriesObserver. Each render it gets back optimisticResult, an array with one result per query, in the order the queries were passed.
  • useSuspenseQueries calls useQueries with every query set to suspense: true and throwOnError: defaultThrowOnError.

throwOnError asks a hook to throw a failed query's error while it renders, instead of returning it. It takes true or a function (error, query) => boolean. shouldThrowError, at packages/query-core/src/utils.ts:470-480, calls the function or coerces the flag to a boolean. defaultThrowOnError, at packages/react-query/src/suspense.ts:11-19, returns query.state.data === undefined. So a suspense query throws only when it has no data to show.

All three hooks ask one function whether to throw: getHasError, at packages/react-query/src/errorBoundaryUtils.ts:51-78. Its body is one expression:

packages/react-query/src/errorBoundaryUtils.ts:70-77 

  return (
    result.isError &&
    !errorResetBoundary.isReset() &&
    !result.isFetching &&
    query &&
    ((suspense && result.data === undefined) ||
      shouldThrowError(throwOnError, [result.error, query]))
  )

errorResetBoundary.isReset() is true just after a QueryErrorResetBoundary has been reset so its queries can run again. None of these conditions asks whether result.error is truthy. The error value only reaches a throwOnError function, as an argument.

Inside useQueries, a render first calls shouldSuspend, which asks whether a query is in suspense mode and still pending. If one is, the hook throws a promise built from fetchOptimistic, which starts the fetch. Otherwise the hook looks for an error to throw. It runs getHasError over optimisticResult with Array.prototype.find and keeps the first result it approves as firstSingleResultWhichShouldThrow. Then comes the guard, an if that decides whether to throw that result's error. The guard is the line this pull request changes.

When a query function rejects, packages/query-core/src/query.ts:601-604 dispatches an 'error' action carrying the rejected value. The reducer at packages/query-core/src/query.ts:672-686 stores that value as state.error and sets status to 'error'. packages/query-core/src/queryObserver.ts:583 derives isError from that status. So Promise.reject() produces a result with isError: true and error: undefined.

Edge case The cache treats undefined differently on success and on failure. A queryFn that resolves with undefined is turned into a thrown Error at packages/query-core/src/query.ts:566-573. A queryFn that rejects with undefined keeps undefined as its error. A result can therefore carry isError: true and a falsy error at once.

Intuition

Picture the result useQueries holds for one query after Promise.reject(). The query sets retry: false, so the first rejection is final: 

{ status: 'error', isError: true, error: undefined, data: undefined, isFetching: false }

getHasError sees isError: true, isFetching: false, and throwOnError: true, and answers yes. Before this change, the guard in useQueries read if (firstSingleResultWhichShouldThrow?.error), which put a second question to the same result: is error truthy? For undefined the answer is no. The hook skipped the throw and returned the result, so the component rendered normally and the boundary's fallback never appeared. After the change the second question is gone. A result that getHasError approved is thrown, whatever its error holds.

useSuspenseQueries hits the same guard, because it is useQueries with suspense: true. There the skipped throw left the component rendering with no data at all.

Key concept getHasError decides whether a result should throw. The error value is only what gets thrown. The old guard checked that value afterward, so an undefined error could skip a throw that getHasError had already approved.

Code walkthrough

Flow: the queryFn rejects with undefined, the Query stores error: undefined, getHasError returns true, the guard in useQueries throws, and the nearest error boundary renders; useSuspenseQueries joins this path through its call to useQueries.

useQueries throws for the first result getHasError approves

The find at packages/react-query/src/useQueries.ts:310-324 returns the matching result object, or undefined when no result qualifies. The pull request changes the guard after it:

packages/react-query/src/useQueries.ts:326-328 

-  if (firstSingleResultWhichShouldThrow?.error) {
+  if (firstSingleResultWhichShouldThrow) {
     throw firstSingleResultWhichShouldThrow.error
   }

The removed line did two jobs. find's return type is QueryObserverResult | undefined, so TypeScript rejects a plain .error read on it. The optional chain, ?., makes that read safe by yielding undefined when there is no result. The pull request body gives this as the reason the optional chain was needed. The .error read then added a condition of its own: throw only when the error value is truthy. For an error of undefined, null, '', or 0 that condition was false. The hook fell through to its normal return at the end of the function and handed the errored result to the component instead of throwing it.

The new line asks only whether find found anything. A result is an object, and an object is always truthy, so the result find returned now always reaches the throw. Inside the if, TypeScript knows the result is defined, so the plain .error read compiles. A truthy error behaves as before: it was thrown then and is thrown now.

This is the shape useQuery already had. Once getHasError says yes, useBaseQuery throws result.error with no check on the value:

packages/react-query/src/useBaseQuery.ts:127-137 

  if (
    getHasError({
      result,
      errorResetBoundary,
      throwOnError: defaultedOptions.throwOnError,
      query,
      suspense: defaultedOptions.suspense,
    })
  ) {
    throw result.error
  }

The new test at packages/react-query/src/__tests__/useQueries.test.tsx:276-307 pins this step. It renders one query with queryFn: () => Promise.reject(), retry: false, and throwOnError: true inside an ErrorBoundary, and expects the boundary's fallback text, "error boundary". The new test at packages/react-query/src/__tests__/useQuery.test.tsx:2776-2803 runs the same setup through useQuery, which never reaches this guard. The pull request body calls it the reference behavior, passing before and after the fix.

useSuspenseQueries reaches the same line on its second render

useSuspenseQueries has no throw of its own. Its body, at packages/react-query/src/useSuspenseQueries.ts:189-211, rewrites each query's options and calls useQueries:

packages/react-query/src/useSuspenseQueries.ts:200-206 

        return {
          ...query,
          suspense: true,
          throwOnError: defaultThrowOnError,
          enabled: true,
          placeholderData: undefined,
        }

Only suspense and throwOnError matter here. So the one-line edit above is the whole fix for this hook too. What differs is the route to the guard, which takes two renders:

On the first render the query is still pending, so shouldSuspend is true. useQueries throws Promise.all over the fetchOptimistic promises at packages/react-query/src/useQueries.ts:307-309. fetchOptimistic attaches a .catch at packages/react-query/src/suspense.ts:73-75, so the thrown promise resolves even though the fetch failed. React sees it settle and renders again.

On the second render the query sits in 'error' with no data. getHasError returns true through its suspense branch, suspense && result.data === undefined, without calling throwOnError at all. Before the fix the guard then read error: undefined, skipped the throw, and returned the result. The component rendered with data set to undefined, although useSuspenseQueries types data as always defined. The project's suspense guide gives that guarantee as the reason these hooks do not let a caller change throwOnError, at docs/framework/react/guides/suspense.md:38. The issue names what follows in user code: a later read of data fails with an unrelated TypeError. After the fix the second render throws undefined, and the ErrorBoundary around the <Suspense> element shows its fallback.

The test at packages/react-query/src/__tests__/useSuspenseQueries.test.tsx:580-614 follows this timeline. Its queryFn waits 10 ms with sleep(10), then rejects with undefined. The test first expects the Suspense fallback, loading. It then lets 10 ms pass so the queryFn rejects, and expects the error boundary's fallback. The pull request body reports that before the fix this component rendered data: undefined instead.

Quiz

A component calls useQueries with two queries, both retry: false and throwOnError: true. The queryFn of the query listed first rejects with null. A moment later, the other rejects with new Error('boom'). What did the component do before this pull request, and what does it do now?

Results keep the order the queries were passed, and find stops at the first one getHasError approves, which is the null query. The old guard read null and skipped the throw. It never looked at the other result, so Error('boom') was not thrown either. The new guard throws for the result find returned, so the boundary receives null. Error('boom') stays on the other query's result.

A useSuspenseQueries query has cached data from an earlier success. A background refetch then rejects with undefined, and that fetch has finished. With this pull request applied, what does the component render?

getHasError returns false here, so find returns undefined and the edited guard has nothing to throw. Its suspense branch needs result.data === undefined, and the cached data fails that. defaultThrowOnError returns query.state.data === undefined, which is false for the same reason. The pull request changed what happens after getHasError says yes, not when it says yes. The component keeps the cached data, and the result's error is undefined.

Someone edits the guard to if (firstSingleResultWhichShouldThrow?.error != null), meaning to throw only real errors. Which of the three new tests in this pull request fail?

The query function in all three tests rejects through Promise.reject(), so the error is undefined, and undefined != null is false. The guard would skip the throw in the useQueries test, and useSuspenseQueries runs through the same guard. The useQuery test never reaches this line, because useBaseQuery has its own throw with no check on the value.
