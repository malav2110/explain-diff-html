The broadcast client keeps sending after an incoming message throws

When applying a message from another tab throws, broadcastQueryClient now clears its transaction flag anyway, so the tab keeps broadcasting its own query changes.

TanStack/query PR 11242 at a631add, explained 2026-11-16. References link to this commit.

Background

New to this area? Expand for the deeper background.

TanStack Query keeps server data in a QueryClient. The client stores each piece of data as a query in its QueryCache. A query key, an array such as ['todos'], names each query, and the queryHash is that key written as a string, '["todos"]'. An observer, such as the one a useQuery call creates, watches one query. The core library's files, cited below, live in packages/query-core/src/.

Three of the cache's event types matter here: added when a query enters, updated when its state changes, and removed when it leaves. Code listens with queryCache.subscribe(listener), which returns a function that removes the listener again. queryCache.notify (queryCache.ts:200-206) calls the listeners one after another, in the order they subscribed. The calls are synchronous. A listener that throws ends the loop, so later listeners miss that event, and the error travels up to whatever code caused the event.

notify runs that loop inside notifyManager.batch (notifyManager.ts:52-64). A batch counts the batches that are open in a counter named transactions, separate from the plugin's transaction flag below, and holds back scheduled notifications until that count returns to zero.

Three calls produce the events on this page. queryCache.build returns the query for a hash, creating it and emitting added if it is new (queryCache.ts:116-127). query.setState(state) (query.ts:249-251) merges state into the query's state and emits updated (query.ts:704-714). queryClient.setQueryData(key, data), the public call for writing data by hand, builds the query and then sets its data, which emits an updated event whose action is success (queryClient.ts:209-211).

A BroadcastChannel lets browser tabs on the same origin message each other. Each tab opens a channel with the same name. When one tab calls postMessage(value), the onmessage handler in every other tab receives a copy of value. broadcastQueryClient takes its BroadcastChannel from the broadcast-channel npm package.

broadcastQueryClient, the plugin this page covers, is in packages/query-broadcast-client-experimental/src/index.ts. It keeps the query caches of several tabs in step by connecting each tab's cache to the channel in two directions:

  • Outgoing: a cache listener (index.ts:112-146) turns each added event, each updated event with a success action, and each removed event for a query that still has observers into a message. It hands each one to safePost (index.ts:77-78), which calls channel.postMessage.
  • Incoming: channel.onmessage (index.ts:148-191) applies another tab's message to this cache. For an added or updated message it calls query.setState when the hash is already cached, and queryCache.build when it is not. A removed message removes the cached query.

When onmessage applies a message, the cache changes and emits events like any other. Without a guard, the outgoing listener would send them straight back out. A boolean, transaction (index.ts:55), is that guard. onmessage runs its work through a helper, tx(cb), which sets transaction to true, calls cb, and sets it back to false. While the flag is true, the outgoing listener returns at its first statement (index.ts:113-115). tx is the only code that writes the flag.

The package's tests replace the real channel with a class, MockBroadcastChannel, whose postMessage is a Vitest spy named mockPostMessage (index.test.ts:8). A spy records each call made to it. expect(spy).toHaveBeenCalled() passes when that record holds at least one call, and spy.mockClear() empties the record.

Intuition

The flag has to be false whenever tx is not running. The old tx cleared it with the statement after cb(), and a statement after a call runs only when the call returns. When cb throws, control leaves tx at the call, and the flag stays true. Until something clears it, the outgoing listener treats every local change as if it came from another tab, and sends nothing.

The fix wraps cb() in try and moves the reset into a finally block.

Key concept try { … } finally { … } runs the finally block on both ways out of the try block: when it completes and when it throws. The finally block catches nothing. When it finishes normally, the error carries on up the stack as if the block were not there. The finally block in tx only assigns the flag, so it always finishes normally.

In row 1 the new tx clears the flag, and the listener's error still comes out of onmessage.

Edge case How long the old flag stayed stuck. The comment the fix adds says that without it transaction "would stay true forever". Row 3 shows a narrower limit, read from the code; no test in the pull request covers it. Because tx is the only writer, the next incoming message that applies without throwing clears the flag. The tab stays silent for the rest of the session only when every later incoming message also throws, or when no other tab sends one.

Code walkthrough

Incoming: a message from another tab → channel.onmessage → tx → queryCache.build or query.setState → queryCache.notify → each cache listener. Then outgoing: a local setQueryData → the outgoing listener → safePost.

tx clears the flag on both ways out of the callback

channel.onmessage drops a message with no type, then passes the rest of its work to tx (index.ts:148-153). The change sits entirely inside tx:

packages/query-broadcast-client-experimental/src/index.ts:56-68 

   const tx = (cb: () => void) => {
     transaction = true
-    cb()
-    transaction = false
+    try {
+      cb()
+    } finally {
+      // Guard against `cb` throwing (e.g. `query.setState`/`queryCache.build`
+      // triggering a listener that throws while applying an incoming
+      // cross-tab message). Without this, `transaction` would stay `true`
+      // forever, silently disabling this tab's own broadcasts to other tabs
+      // for the rest of the session.
+      transaction = false
+    }
   }

The callback is the body of onmessage (index.ts:153-190). For a cached hash it calls query.setState (index.ts:160), and for a new hash it calls queryCache.build (index.ts:164-171). Both end in queryCache.notify. When a listener throws there, the error passes up through these frames. The list shows the build path, outermost frame at the top:

  1. 1channel.onmessage, called with the message
  2. 2tx, which set transaction and called cb
  3. 3cb, the body of onmessage
  4. 4queryCache.build, for a hash not yet cached
  5. 5queryCache.add, which stores the query, then notifies
  6. 6queryCache.notify
  7. 7notifyManager.batch, around the listener loop
  8. 8the app's listener, which throws

Of these frames, notifyManager.batch already decrements its transactions counter in a finally block (notifyManager.ts:57-58), so the counter is back in step by the time the error reaches tx. tx now does the same for its flag, by the rule in the Intuition callout. Once the flag is clear, the same error continues out of onmessage, and the outgoing listener's guard (index.ts:113-115) lets the next local event through.

Quiz

notifyManager.batch guards its transactions counter with the same try/finally shape that tx now uses for a boolean. Under what condition would tx need a counter too?

A counter matters only when the guarded code can re-enter itself. With a boolean, an inner tx would set the flag to false in its finally while the outer callback was still applying its message, and the outer call's remaining cache events would be sent to other tabs. notifyManager.batch does re-enter itself: query.setState opens a batch, and queryCache.notify opens another inside it, so a counter is what lets the outer batch know it is still open. Two tabs sending at once does not nest, because each message arrives as its own event, and JavaScript runs one handler to completion before it starts the next. Several throwing listeners still mean one exit from tx. Asynchronous work that runs after tx returns is outside the flag whichever type the flag has.

In the test that writes ['existing'] before the bad message, delete the line mockPostMessage.mockClear(). Then run the edited test against the old tx. What happens?

The test writes ['existing'] while the flag is still clear, and that write calls mockPostMessage for its added and updated events. Without mockClear(), those calls are still on record when the last assertion runs, so toHaveBeenCalled() passes whether or not ['local2'] was ever sent. An assertion that a setup step already satisfied cannot fail. The throwing listener is removed before the local write, so nothing throws there, and onmessage throws exactly as before, since the deleted line runs after it.

Under the new code, an app subscribes a cache listener after calling broadcastQueryClient. The listener throws on every updated event and is never removed. This tab then calls setQueryData on a key that is not cached yet. What happens?

Only tx sets the flag, and only incoming messages run tx, so a local write made outside an incoming message never meets a set flag. setQueryData builds the query, which emits added, and then sets its data, which emits updated with a success action. In each notification the outgoing listener runs before the app's, because it subscribed earlier, so it posts both messages. On the updated event the app's listener then throws. Nothing on the local path catches the error, so it reaches the code that called setQueryData.
