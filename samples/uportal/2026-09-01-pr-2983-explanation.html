uPortal PR 2983: skin and JSP asset URLs point at /resource-server

This pull request points uPortal core's asset URLs at the /resource-server/ context instead of the legacy /ResourceServingWebapp/ one, including three libraries whose skin entries picked up the legacy prefix at run time while that webapp was deployed, and it stops loading lodash, modernizr, normalize.css, and four polyfills.

uPortal-Project/uPortal PR 2983 at 0468c6d, explained 2026-11-16. References link to this commit.

Background

New to this area? Expand for the deeper background.

uPortal is a Java web application, shipped as a war, a web application archive. Tomcat, the server it runs in, can host several web applications at once, and each one answers under its own context path: the portal under a path such as /uPortal, an asset server under /resource-server. A browser that requests /resource-server/rs/underscore/1.8.3/underscore.js reaches whichever application owns /resource-server.

One application can look up another by its context path with the servlet method ServletContext.getContext. Tomcat answers only when the asking application allows cross-context access, and uPortal does: META-INF/context.xml:21 sets crossContext="true".

A uPortal page is rendered on the server. A theme stylesheet, respondr.xsl, writes the page's <head>, and each portlet on the page adds a fragment rendered from a JSP. A JSP calls Java code through tags from a tag library. Every JSP in this change includes include.jsp, which declares the prefix c: for the standard JSTL core tags at include.jsp:21 and rs: for the resource-server tags at include.jsp:30. <c:set var="x" value="..."/> stores a string in a page variable, and ${x} reads it back.

A skin descriptor lists most entries twice: once with included="plain" for the readable file, and once with included="aggregated" for the minified one. The portal loads one set on every page. It loads the aggregated set unless the Java system property org.jasig.resourceserver.utils.aggr.aggregated_theme is false. For the aggregated set it reads skin.aggr.xml, a copy of the descriptor that the build writes with local files merged. Absolute entries pass through that copy unchanged (ResourcesAggregatorImpl.java:262-264, in resource-server-core 1.5.3).

lodash and underscore are JavaScript utility libraries with overlapping functions, and each installs itself as a global named _. The theme loads underscore 1.8.3 and then, at respondr.xsl:274, stores it as up._ with _.noConflict(), which gives the global _ back to whatever held it before.

The pull request body gives the reason for the change. uPortal-start, the project that assembles and deploys a full portal, is about to retire its ResourceServingWebapp overlay, the build project that deploys the legacy asset server. Before that happens, every reference in uPortal core to /ResourceServingWebapp/... has to land on /resource-server/..., which resource-server-webapp 1.5.x serves and which the body calls the modern context. The commit messages report that the files these references name, among them the tango and famfamfam icon sets, are byte-identical at the new paths. The head commit says it checked its three libraries with curl against a running portal.

A skin descriptor is an XML file, such as skin.xml or common_skin.xml, that lists a skin's CSS and JavaScript files. The portal turns each entry into an element in the page's head. respondr.xsl:640-642 calls the skinResources template with SKIN_RESOURCES_PATH, the path of the skin's skin.xml (respondr.xsl:152). The template, at resourcesTemplates.xsl:36, hands that path to the provider, ResourcesElementsProviderImpl, a class in the resource-server-utils 1.5.3 library from org.jasig.resourceserver. The provider reads the descriptor and returns one <script> or <link> element per entry. The default skin's skin.xml pulls in the shared common_skin.xml at skin.xml:50, so the shared entries reach every page on that skin.

Key concept The provider handles an entry in one of three ways, by its path and its resource attribute. A path that starts with none of /, http://, or https:// is relative, and it gets the skin's folder in front. Any other path is absolute, and the provider writes it to the page as it stands. An absolute path marked resource="true" goes instead to a resolver, resolveResourceUrl, which picks a context path to put in front while the page renders. This page calls such an entry a resolver entry.

The rs: tags come from the same library. <rs:resourceURL value="/rs/..."/> turns a path into a URL and prints it, or stores it in a page variable when the tag has a var attribute. <rs:compressJs> wraps an inline script. Its javadoc says it once minified the script with YUI Compressor. In 1.5.3 it is marked @Deprecated and copies its body through unchanged (JavaScriptMinificationTag.java:46-50, in resource-server-utils).

Two portlet JSPs loaded lodash 4.17.4 themselves, through <rs:resourceURL>, and called it as _. sitemap.jsp builds a sitemap from the layout API, /api/v4-3/dlm/layout.json, and checks the JSON with its own helper, sitemapJsonCheck, before it reads a key. searchRest.jsp builds one tab of results per result type from the search API, /api/v5-0/portal/search, which answers with an object such as {"people": [...], "portlets": [...]} (SearchRESTController.java:144-151). The lodash calls were _.has, which tests a dotted key path; _.every, _.forEach, and _.forOwn, which loop; _.unescape, which decodes HTML entities; and _.startCase and _.kebabCase, which turn peopleTab into People Tab and people-tab.

Intuition

A page can ask /ResourceServingWebapp for a file in two ways. The first is a string that says so, such as /ResourceServingWebapp/rs/fontawesome/4.7.0/css/font-awesome.min.css in the old skin.xml. A text search for ResourceServingWebapp finds it. The second is a path with no context in it, such as /rs/underscore/1.8.3/underscore.min.js, marked resource="true". That path names no server at all until the resolver adds one while the page renders.

The provider and its resolver decide like this:

flowchart TD
  A["A js or css entry in a skin descriptor"] --> B{"Starts with / or http:// or https://?"}
  B -->|no| C["Prefix the skin folder"]
  B -->|yes| D{"resource is true?"}
  D -->|no| E["Emit the path as written"]
  D -->|yes| F{"/ResourceServingWebapp deployed and holds the file?"}
  F -->|yes| G["Prefix /ResourceServingWebapp"]
  F -->|no| H["Prefix the portal context path"]
  classDef touched fill:#e8eefc,stroke:#3b6cf6,color:#16181b
  classDef caveat fill:#fbefe1,stroke:#b5620a,color:#16181b
  class E touched
  class G caveat

The resolver's default context is "/ResourceServingWebapp" (ResourcesElementsProvider.java:58, the interface the provider implements). A resourceContextPath context parameter in the portal's web.xml would replace it, and uPortal sets none. The last check asks Tomcat, through getContext, for the web application at that path, which crossContext="true" permits. It then asks that application whether it holds the file. So on a portal that still runs the legacy webapp, the underscore entry becomes a request to it, although no line of uPortal names it.

Before: the resolver picks the server

common_skin.xml entry
/rs/underscore/…
resolveResourceUrl
/ResourceServingWebapp/rs/…
legacy webapp

After: the entry names the server

common_skin.xml entry
/resource-server/rs/…
resource-server webapp

The fallback branch would not have rescued these entries. When the lookup fails, the resolver puts the portal's own context path in front. The build copies the rs/ folder of resource-server-content 1.5.3 into the portal's war (build.gradle:139-146), but that copy holds underscore.js and underscore-min.js, not underscore.min.js, and no .min.js file for backbone or the rating plugin. On the default aggregated set, the fallback would name files that copy lacks. That fits the head commit's statement that dropping the overlay would otherwise leave these scripts unresolved.

Writing the context into the path settles the choice in the file rather than at deployment. An absolute path without the attribute never reaches the resolver, so every deployment requests the same server. The pull request's earlier commit, c80cdea43, rewrote the literal /ResourceServingWebapp/... strings and left the resolver entries for underscore, backbone, and the rating plugin as they were. The record does not say how that commit chose its targets. The head commit, 0468c6d, rewrote the resolver entries. Its message says a uPortal-start smoke test caught them once it visited an admin page, uportal-links?pCm=config, and the pull request body says that suite asserts the absence of legacy URL requests.

The rest of the change removes requests instead of redirecting them. The descriptors drop libraries the author judged unused or covered by the browser, and two JSPs replace lodash with plain JavaScript.

Code walkthrough

Flow map: page request → respondr.xsl writes the head from skin.xml and common_skin.xml → portlet JSPs add their own scripts → icon URLs in CSS, JavaScript, JSPs, and portlet data → the browser fetches the repointed files from /resource-server/.

So the portal itself can serve both.

The jqueryui i18n entries at common_skin.xml:51-54 still name /ResourceServingWebapp, inside an XML comment. The head commit's message leaves them as inactive markup, so a text search after this change still finds them.

The default skin's own descriptor has one string to fix. 2. The skin descriptors drop modernizr, normalize.css, and the polyfills

Some entries are deleted rather than repointed, and a dated comment takes each block's place. The polyfills, scripts that add browser features older browsers lack, go from near the end of common_skin.xml:

uPortal-webapp/src/main/webapp/media/skins/respondr/common/common_skin.xml:104-106 

-    <!-- ES6&7 polyfill -->
-    <js included="plain" resource="true">/webjars/core-js-bundle/index.js</js>
-    <js included="aggregated" resource="true">/webjars/core-js-bundle/minified.js</js>
     (elided: the same deletion for regenerator-runtime, whatwg-fetch, and webcomponents)
+    <!-- ES6+/fetch/async-await/Web-Components polyfills removed 2026-05-06.
+         uPortal targets Bootstrap 5 baseline browsers (no IE), all of
+         which natively support these APIs. Polyfills were dead weight. -->

modernizr, a feature-detection library, goes from the top of common_skin.xml, and its comment sits at common_skin.xml:26-27. normalize.css, a stylesheet that evens out browser defaults, goes from skin.xml, with its comment at skin.xml:28-29.

Each comment gives the author's reason. For modernizr, the reason is that no code calls Modernizr, and that holds within this repository: at this commit, the name appears only in the comment and twice in an architecture document, in a table of outdated libraries and in a list of libraries to remove. The other reasons are claims about supported browsers: that Bootstrap 5's reboot.css does the job of normalize.css, and that the browsers Bootstrap 5 supports have the polyfilled features natively. The diff does not test them.

Edge case The diff touches no build file. build.gradle:97 and build.gradle:99-101 still declare the core-js-bundle, regenerator-runtime, webcomponentsjs, and whatwg-fetch webjars, so the build still unpacks those files into the war. What this change stops is the page asking for them.

<rs:resourceURL> hands its value to the same resolveResourceUrl that resolver entries go through (ResourceIncludeTag.java:58, in resource-server-utils). <c:set> stores exactly the string it is given. 4. sitemap.jsp and searchRest.jsp drop lodash

Both files delete the same line, the one that loaded lodash:

Removed from sitemap.jsp and searchRest.jsp

-<script src="<rs:resourceURL value="/rs/lodash/4.17.4/lodash.min.js"/>"></script>

That tag was one more trip through the resolver. The earlier commit's message gives the reasons to drop lodash rather than repoint it: four CVEs against 4.17.4, CVE-2018-3721, CVE-2019-10744, CVE-2020-8203, and CVE-2021-23337, and calls that plain JavaScript can replace. Once the tag is gone, _ no longer names lodash in these files. Underscore is no stand-in, because the theme keeps it at up._, not _. So each _. call is rewritten in plain JavaScript.

In sitemap.jsp, sitemapJsonCheck at sitemap.jsp:93-101 takes an object and a list of paths, pathChecks, and returns true when a path is missing. Inside it, pathChecks.every replaces _.every and asks the key test about each path, and a leading ! flips the answer, as it did before. The check at sitemap.jsp:119 throws when 'layout.navigation.tabs' is absent, and the checks at sitemap.jsp:127, sitemap.jsp:138, and sitemap.jsp:143 skip the item that lacks a key. lodash's _.has took a dotted path and walked it one key at a time, testing own properties. hasPath walks it the same way with a loop, but tests each key with in, which also accepts inherited keys. For the keys this file checks, the answer is the same:

uPortal-webapp/src/main/webapp/WEB-INF/jsp/Invoker/sitemap.jsp:74-83 

+    function hasPath(obj, dotPath) {
+        var parts = dotPath.split('.');
+        for (var i = 0; i < parts.length; i++) {
+            if (obj == null || typeof obj !== 'object' || !(parts[i] in obj)) {
+                return false;
+            }
+            obj = obj[parts[i]];
+        }
+        return true;
+    }

The loops over tabs and portlets at sitemap.jsp:126, sitemap.jsp:137, and sitemap.jsp:142 become Array.prototype.forEach. _.unescape becomes unescapeHtml at sitemap.jsp:85-90. It decodes the entities lodash 4.17.4 decodes, &amp;, &lt;, &gt;, &quot;, and &#39;, plus &#96;. So a tab or portlet name that arrives with &#96; now shows a backtick, where lodash left the entity text on screen.

searchRest.jsp used lodash to turn each key of the search response into a tab. _.startCase made the tab's label, and _.kebabCase made its element id. Two small helpers stand in for them:

uPortal-webapp/src/main/webapp/WEB-INF/jsp/Search/searchRest.jsp:138-150 

+function startCase(s) {
+    return s.replace(/([a-z])([A-Z])/g, '$1 $2')
+            .replace(/[-_]+/g, ' ')
+            .replace(/\s+/g, ' ')
+            .trim()
+            .replace(/\b\w/g, function (c) { return c.toUpperCase(); });
+}
+// "peopleTab" -> "people-tab"
+function kebabCase(s) {
+    return s.replace(/([a-z])([A-Z])/g, '$1-$2')
+            .replace(/[\s_]+/g, '-')
+            .toLowerCase();
+}

For the keys the search API sends, the output is what lodash gave: startCase('people') is People, and kebabCase('portlets') is portlets. The loop over the response changes shape too. _.forEach over an object passed each value with its key, while Object.keys(response).forEach passes only the key, tabProperty. So searchRest.jsp:194 reads response[tabProperty] itself. The _.forOwn loop over a result's attributes, at searchRest.jsp:233-236, gets the same treatment. Its i18n.hasOwnProperty(attributeName) becomes Object.prototype.hasOwnProperty.call(i18n, attributeName), which gives the same answer for i18n, a plain object literal.

Edge case startCase also formats each attribute label, at searchRest.jsp:242, which adds a colon after it. Those labels come from the message bundles. The helper's last step, \b\w, counts only ASCII letters, digits, and the underscore as word characters, so an accented letter ends a word. The French label for givenName is Pr\u00E9nom at Messages_fr.properties:70, which reads Prénom, and the one at Messages_fr.properties:75 reads Téléphone. When a label reaches the script in that form, the helper shows PréNom: and TéLéPhone:. lodash's _.startCase stripped accents first, with deburr (lodash.js:5009, in lodash 4.17.4), so it showed Prenom: and Telephone:. The exact input depends on the response encoding, because include.jsp:35 turns on Spring's HTML escaping for the message tag.

Quiz

uPortal-start has retired ResourceServingWebapp, and the portal runs at /uPortal. Which URL does the aggregated jstree entry at common_skin.xml:100 put on the page?

The jstree entry still carries resource="true", so the provider sends it to resolveResourceUrl. With no /ResourceServingWebapp context to find, the resolver falls back to the request's own context path, /uPortal. The build unpacks the jstree webjar into the portal's war, and that webjar holds dist/jstree.min.js, so the file is there. Nothing in this change moves the resolver's default away from /ResourceServingWebapp, and a path goes to the page unchanged only when the attribute is absent.

Suppose hasPath in sitemap.jsp were replaced by Object.prototype.hasOwnProperty.call(obj, dotPath), an own-property check on the whole string. What would a user see where the sitemap belongs?

The check at sitemap.jsp:119 passes the dotted path 'layout.navigation.tabs'. No object has an own property named with that whole string, so the check reports it missing for every response. The next line throws, and the .catch at sitemap.jsp:179-185 appends the error.loading.sitemap message, "Unable to load sitemap." in English. The checks on tabs and portlets pass single key names and would still work, but the code never reaches them.

The three libraries' entries could have kept resource="true" instead of naming /resource-server/ in the path. When would keeping the attribute have been the better choice?

The resolver falls back to the portal's own context path whenever it cannot find the legacy webapp or the file in it, so a resolver entry still loads on a portal whose war holds the file. A path written into the entry always asks /resource-server, and fails where that webapp is absent. This portal's war lacks the minified files the aggregated entries name, so here the fallback would not have served them. The resolver never looks for /resource-server: while the legacy webapp is deployed and holds the file, the attribute sends the request there, which is what this change removes. The included value picks the readable or the minified file, and both kinds follow the same path rules.

Before this change, a portal ran both asset webapps, and the legacy one held the canvg file. What value did reportGraph.jsp store in canvgScriptPath?

<rs:resourceURL> sends its value through resolveResourceUrl, the same resolver as a skin entry with resource="true". The resolver's default context is /ResourceServingWebapp, the cross-context lookup finds that webapp, and the webapp holds the file, so the resolver puts that context in front. With var, the tag stores the result instead of printing it. A /uPortal/... value is the fallback for a failed lookup, and /resource-server/... is what the new <c:set> line stores.

The earlier commit in this pull request missed three libraries whose skin entries a text search for ResourceServingWebapp cannot find, and a browser test caught them. Which general point does that illustrate?

The entries held /rs/... paths, and the resolver added /ResourceServingWebapp only while a page rendered, so no line of source contained the string. A test that watches the requests a rendered page makes sees each URL after it is built. The other claims describe real hazards, not this miss: the entries named no server at all, the resolver's cache cannot hide a string that was never in the file, and the fix itself writes absolute paths.
