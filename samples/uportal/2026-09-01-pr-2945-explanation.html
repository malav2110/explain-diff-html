PR 2945: each limiting tee's callback becomes a Consumer

The limit-reached callback in LimitingTeeWriter and LimitingTeeOutputStream changes from Guava's Function to Consumer, so firing it returns nothing for ErrorProne's CheckReturnValue check to flag.

uPortal-Project/uPortal PR 2945 at a20fb52, explained 2026-11-16. References link to this commit.

Background

New to this area? Expand for the deeper background.

A tee is named after the Unix tee command: it sends one stream of output to two places. uPortal's TeeWriter passes every write to its main writer, out, and then repeats it on a second writer, the branch (uPortal-utils/uPortal-utils-core/src/main/java/org/apereo/portal/utils/TeeWriter.java:63-66). TeeOutputStream does the same for bytes. The two extend commons-io's ProxyWriter and ProxyOutputStream, and those call a hook, beforeWrite(n), with the size of each write before passing it on.

A Java lambda is an object that implements an interface with one abstract method, and that interface decides whether the lambda must return a value. Guava's com.google.common.base.Function<F, T> declares T apply(F input) and returns a value, while the JDK's java.util.function.Consumer<T> declares void accept(T t) and returns none.

ErrorProne is a compiler plugin that adds checks to javac, and uPortal applies it to every subproject (build.gradle:46). Its CheckReturnValue check flags a call that throws away the result of a method annotated @CheckReturnValue, the marker a library puts on methods whose result the caller must use. This pull request's body calls the failure it avoids "the underlying Guava @CheckReturnValue check".

A uPortal page is assembled from portlets, and uPortal can cache a portlet's rendered output. For each render, PortletRendererImpl builds a CachingPortletOutputHandler with a size threshold (PortletRendererImpl.java:435-436). Its constructor stores that threshold as maximumSize (CachingPortletOutputHandler.java:45). CachingPortletOutputHandler gives the portlet a character writer from getPrintWriter() or a byte stream from getOutputStream(). Behind the writer sits a LimitingTeeWriter, and behind the stream a LimitingTeeOutputStream. These limiting tees extend TeeWriter and TeeOutputStream, which send each write to two places: out, the real response, and branch, an in-memory copy for the cache.

Each limiting tee receives maximumSize as maximumCharacters or maximumBytes. It overrides beforeWrite, the hook commons-io calls with the size of every write, to keep a running count. On the write that takes the count past the maximum, the tee sets limitReached, swaps the branch for a NullWriter or NullOutputStream through setBranch, and calls its limitReachedCallback. The callback that CachingPortletOutputHandler supplies runs clearCachedWriter() (CachingPortletOutputHandler.java:179-186) or clearCachedStream() (CachingPortletOutputHandler.java:195-199), which empties the partial copy. getCachedPortletData then returns null, so the render is not cached (CachingPortletOutputHandler.java:50-54). The callback is optional: each tee's three-argument constructor passes null in its place (LimitingTeeWriter.java:36-38).

Intuition

A callback's type tells the code that calls it whether there is a result to use. Compare two toy callbacks: 

Function<String, Integer> length = s -> s.length();
Integer n = length.apply("abc");     // n is 3, and the caller keeps it

Consumer<String> print = s -> System.out.println(s);
print.accept("abc");                 // prints abc; there is no result

The limiting tees use their callback the way this code uses print: they call it for its effect and never read a result. Their field was typed like length, though, so every apply(this) produced a value with nowhere to go. Under the newer Guava, CheckReturnValue flags that dropped value. PR 2943 gave the value somewhere to go: a local named unused. That cost a local nobody reads, a @SuppressWarnings("unused") annotation against unused-variable warnings, and a two-line comment. The commit message puts the case for the new type this way: "the callback's return was always discarded (the ? wildcard on Function was a tell)".

With Consumer, accept(this) returns void. There is no value to keep or drop, so the call needs no workaround.

What stays the same The pull request body says "no behavior change". The callback still runs once, on the write that crosses the limit, and still clears the cached copy.

2. The tee stores a Consumer and calls accept

On the receiving side, LimitingTeeWriter retypes its field, and the matching parameter of its four-argument constructor, as Consumer<LimitingTeeWriter> (LimitingTeeWriter.java:32 and LimitingTeeWriter.java:44). An import of java.util.function.Consumer replaces Guava's (LimitingTeeWriter.java:19), and the class Javadoc now links Consumer (LimitingTeeWriter.java:27). The call itself is the last statement of the hook:

uPortal-rendering/src/main/java/org/apereo/portal/portlet/container/cache/LimitingTeeWriter.java:74-89 

@Override
protected void beforeWrite(int n) throws IOException {
    this.characterCount += n;

    if (this.maximumCharacters > 0
            && !this.limitReached
            && this.characterCount > this.maximumCharacters) {
        // Hit limit, replace tee'd writer with a null writer
        this.limitReached = true;
        this.setBranch(NullWriter.NULL_WRITER);

        if (this.limitReachedCallback != null) {
            this.limitReachedCallback.accept(this);
        }
    }
}

The four removed lines shown in Background become the single accept(this) call at LimitingTeeWriter.java:86. That call runs the lambda from step 1. The null guard around it is unchanged.

LimitingTeeOutputStream gets the same edit and counts bytes instead of characters. Its field is at uPortal-rendering/src/main/java/org/apereo/portal/portlet/container/cache/LimitingTeeOutputStream.java:32, its parameter at LimitingTeeOutputStream.java:44, and its call at LimitingTeeOutputStream.java:84.

Edge case Both four-argument constructors are public. Code outside this repository that passes a Guava Function object, such as an anonymous class or a variable, stops compiling against them. A lambda whose body is a single method call still compiles, because Consumer accepts it too. A search of src/main at this commit finds no caller of either tee other than CachingPortletOutputHandler.

Quiz

Suppose this pull request had kept the tee's parameter as Guava's Function<LimitingTeeWriter, ?> and changed only the caller to input -> clearCachedWriter(). What happens at build time?

clearCachedWriter() is declared void (CachingPortletOutputHandler.java:179). A lambda aimed at Function<LimitingTeeWriter, ?> has to produce an Object for apply to return, and a call to a void method produces none, so javac rejects it. Java never adds a return null for you, and the wildcard does not become Void. That is why the old anonymous classes ended with an explicit return null;, and why the short lambda depends on the type change in step 2.

JpaPortalEventStore passes each stored event to the Function<PortalEvent, Boolean> handler that IPortalEventDao.aggregatePortalEvents takes. Suppose someone retyped that handler as Consumer<PortalEvent>, the way this pull request retyped the tee's callback. What would the store lose?

The Boolean is a result the store reads. JpaPortalEventStore.java:287-292 keeps it as eventHandled and returns false, ending the batch, when the handler returns false. The interface's Javadoc asks handlers to do exactly that when aggregation should stop (IPortalEventDao.java:62-64). A Consumer has no result to give. The tee's ? wildcard was the opposite case: nothing read the result, so there was no result type worth keeping.

The if (this.limitReachedCallback != null) guard in LimitingTeeWriter.beforeWrite survived this change. What would fail if it were deleted?

The three-argument constructor stores null as the callback (LimitingTeeWriter.java:36-38), and testContentExceedsThreshold builds one that crosses the limit (LimitingTeeWriterTest.java:42-43). Without the guard, the write that crosses the limit calls accept on null and throws a NullPointerException. Any reference type can hold null, a Consumer included, and javac accepts the call. Repeat calls are prevented by a different condition, !this.limitReached, which beforeWrite tests before it reaches the callback.
