A callback that never returned anything useful, typed to say so

uPortal PR 2945 changes the callback that uPortal's two limiting tees call when output passes a size limit from Guava's Function<T, ?> to Java's Consumer<T>, so the result that ErrorProne asked about no longer exists and the workaround PR 2943 added comes out.

uPortal-Project/uPortal PR 2945 at a20fb52, explained 2026-10-22. References link to this commit.

Background

New to this area? Expand for the deeper background.

uPortal is an open source enterprise portal framework built for higher education. A portal page is assembled from portlets, small applications that each render one fragment of the page. uPortal can capture a portlet's output and reuse it for a later request instead of rendering the portlet again.

A tee, named after the Unix tee command, sends everything written to it to two places. uPortal's TeeWriter (TeeWriter.java:25) wraps a main writer, called out, and a second writer called the branch. Each write goes to out first and to the branch second. TeeWriter extends Apache Commons IO's ProxyWriter, which calls a beforeWrite(n) hook with the number of characters before they reach the main writer. A subclass overrides that hook to watch the traffic, and calls setBranch (TeeWriter.java:34) to swap the branch for another writer. TeeOutputStream does the same job for bytes.

Guava's com.google.common.base.Function<F, T> and Java's java.util.function.Consumer<T> are both functional interfaces: interfaces with a single abstract method, which a lambda can implement. Function declares T apply(F input), so every call returns a value. Consumer declares void accept(T t), so a call returns no value. A field typed Function<T, ?> uses the wildcard ? for the result: the callback returns a value, and the field does not say what kind.

ErrorProne is a Google compiler plugin that adds checks to javac. Its CheckReturnValue check reports a call whose result is thrown away when the method, its class, or its package is marked @CheckReturnValue. Guava marks its whole com.google.common.base package that way (package-info.java:58 in Guava v31.1), so a call that drops the result of Function.apply is the kind the check looks for. A call whose result is assigned to a variable is not dropped, and the check leaves it alone. uPortal applies the ErrorProne plugin in its shared build setup (build.gradle:46).

CachingPortletOutputHandler (CachingPortletOutputHandler.java:30) captures a portlet's output for reuse. Its Javadoc (CachingPortletOutputHandler.java:26-29) says it caches up to maximumSize bytes or characters and gives up caching past that. PortletRendererImpl builds the handler with the portal's cache size threshold (PortletRendererImpl.java:434-436). That threshold, cacheSizeThreshold, defaults to 102400, which the code comment calls 100 KB (PortletCacheControlServiceImpl.java:73-74). A portal operator can override it through the cacheSizeThreshold property that sits commented out at portal.properties:383.

The handler does its capturing with a tee. When the portlet asks for a writer through getPrintWriter, the handler wraps the real response writer in a LimitingTeeWriter and makes an in-memory StringBuilderWriter, its cachingWriter, the branch. A portlet that asks for bytes through getOutputStream gets the same treatment from LimitingTeeOutputStream and a ByteArrayOutputStream. The limiting tee counts what passes through. Once the count goes over the limit, it swaps the branch for NullWriter.NULL_WRITER, a writer that discards everything, and it calls a callback held in a field named limitReachedCallback. The handler's callback empties the partial copy through clearCachedWriter() or clearCachedStream(). Later, the handler's getCachedPortletData checks each tee's isLimitReached() and returns nothing for a tee that hit its limit.

That callback is what this change retypes. Before PR 2943, the tee called this.limitReachedCallback.apply(this); and dropped the result. PR 2943, titled "Fixes for guava version bump", assigned the result to a local variable named unused, which its code comment says satisfies CheckReturnValue. It also put @SuppressWarnings("unused") on that local, so a variable nobody reads raises no warning of its own. PR 2945 removes that workaround and changes the type instead. Its body calls the Consumer version the cleaner design for the same problem.

The PR body also says why the change arrived as a separate pull request. According to the body, the Consumer version was first written as commit f2e3a459 on the remove_fluid branch, the branch behind PR 2915, and reached PR 2943's branch only after PR 2943 had merged. PR 2943's timeline shows its one commit, adcfd74, and the merge. A merged pull request no longer follows its branch, so that timeline cannot confirm the later push.

Key concept A callback's return type is part of its contract. Function<T, ?> tells every caller that a result comes back and is theirs to handle. Consumer<T> tells them nothing comes back. A check about ignored results can only fire where a result exists.
Open question: what made the check fire Commit 8e350c7, the main-branch commit just before PR 2943 merged, carried the plain apply(this) call with the same Guava 31.1-jre pin this page's commit has (gradle.properties:65), so the check was evidently not failing that build. The PR body places the failure on remove_fluid, which pins the resource-server dependency at 1.5.2, set in commit 163e595. This page's commit still pins 1.3.1 (gradle.properties:98). resource-server 1.5.2 declares Guava 32.0.0-android, so this page infers that the bump brings a newer Guava in. Guava 31.1 already carries the annotation, though, so the version alone does not explain it. The dependencies Gradle resolves on remove_fluid would settle the question, and this page did not read them.

Intuition

The tee calls its callback for a side effect: empty the partial copy. It never reads anything back. PR 2943 kept a type that promises a result, then had to explain at the call site why the result was dropped. PR 2945 changes the type to one that promises no result, and the call site has nothing left to explain.

Take a toy limit of 10 characters. A portlet writes Hello, , which is 7 characters, and then portal!, 7 more.

On the second write, beforeWrite sees a count of 14. It swaps the branch for the null writer before portal! reaches the branch, then calls the callback, which empties the 7 characters already copied. The response gets all 14 characters. The cache gets none, and getCachedPortletData returns null.

Nothing on that path uses a value coming back from the callback. The three versions of the call site differ only in how they deal with a value nobody wants:

Version Callback type Call site Workaround
Before PR 2943 Function<LimitingTeeWriter, ?> apply(this); (result dropped) none
PR 2943 Function<LimitingTeeWriter, ?> Object unused = ...apply(this); a local named unused, plus @SuppressWarnings("unused")
PR 2945 Consumer<LimitingTeeWriter> accept(this); none needed

The same reasoning explains the one Function the PR keeps. The PR also edits PortalRawEventsAggregatorImplTest, which drops a Function.apply result of its own. That function is the per-event callback that IPortalEventDao.aggregatePortalEvents takes, and its Boolean result tells the event data-access object (DAO) whether to keep going. That result means something, so the type keeps returning one, and the test assigns the value it drops to a local named ignored instead.

3. The tee fires it once

beforeWrite adds each write to the count, then checks the limit.

uPortal-rendering/src/main/java/org/apereo/portal/portlet/container/cache/LimitingTeeWriter.java:75-88 

protected void beforeWrite(int n) throws IOException {
    this.characterCount += n;

    if (this.maximumCharacters > 0
            && !this.limitReached
            && this.characterCount > this.maximumCharacters) {
        // Hit limit, replace tee'd writer with a null writer
        this.limitReached = true;
        this.setBranch(NullWriter.NULL_WRITER);

        if (this.limitReachedCallback != null) {
            this.limitReachedCallback.accept(this);
        }
    }

!this.limitReached keeps the block from running a second time. The callback runs after the branch swap, so by the time the handler empties the copy, nothing more can land in it. These are the lines PR 2945 removes from the same spot, quoted from the diff:

4. What the callback does, and what the handler returns

The lambda from step 1 calls clearCachedWriter, which deletes everything the copy holds. PR 2945 does not change it.

uPortal-rendering/src/main/java/org/apereo/portal/portlet/container/cache/CachingPortletOutputHandler.java:179-186 

private void clearCachedWriter() {
    if (this.cachingWriter != null) {
        final StringBuilder builder = this.cachingWriter.getBuilder();
        if (builder.length() > 0) {
            builder.delete(0, builder.length());
        }
    }
}

When the portal later asks for the captured output, the handler checks the tee's flag first.

uPortal-rendering/src/main/java/org/apereo/portal/portlet/container/cache/CachingPortletOutputHandler.java:50-53 

if ((this.teeWriter != null && this.teeWriter.isLimitReached())

    // Hit the caching limit, nothing to return

So the callback and the flag split the work. The flag keeps an oversized copy from being cached. The callback empties the partial copy as soon as the limit trips, while the portlet is still writing.

Quiz

The aggregator test keeps Guava's Function and names the result it drops. For the tee's limitReachedCallback, which situation would have made keeping a Function the right type?

A result type earns its place when the caller reads the result, as aggregatePortalEvents reads the per-event callback's Boolean. A callback on another thread still has nothing useful to return. Consumer<LimitingTeeWriter> already receives the tee as its argument, so needing the tee is no reason to keep Function. Where ErrorProne runs changes whether a warning shows up, not which type states the contract.

A handler is built with a maximumSize of 10. The portlet writes abcdefghij and then k. When does the callback fire, and what is left in the cache copy?

The check is characterCount > maximumCharacters. After abcdefghij the count is 10, which is not over 10, so the copy keeps all ten characters. The k takes the count to 11. The tee swaps in the null writer before k reaches the branch, and the handler's lambda empties the ten characters already copied. The response still gets all eleven.

Suppose a CachingPortletOutputHandler were built with a maximumSize of 0. What happens to the portlet's output?

The check in beforeWrite opens with this.maximumCharacters > 0, so a limit of 0 never trips. The tee copies everything, the callback never runs, and getCachedPortletData returns the full copy. A maximumSize of 0 removes the limit; it does not turn caching off.

Suppose the field had stayed Function<LimitingTeeWriter, ?>, but the handler still passed input -> clearCachedWriter(). What happens?

clearCachedWriter() returns void, so input -> clearCachedWriter() has no value to hand back. A Function must return one, so javac rejects that lambda for a Function<LimitingTeeWriter, ?>. That is why the old anonymous classes ended with return null;. A Consumer expects no value, so the short lambda fits it.

Suppose the this.setBranch(NullWriter.NULL_WRITER) line in beforeWrite were deleted, and nothing else changed. What happens once the output passes the limit?

The callback still empties the copy once. The branch stays the caching writer, though, so the write that crossed the limit and every write after it land in the copy again. getCachedPortletData still returns null, because isLimitReached() is true, so nothing stale is served. The !this.limitReached guard keeps the callback to a single call, and the response never depended on the branch.
