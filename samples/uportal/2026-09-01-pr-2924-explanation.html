uPortal PR 2924: a stale portlet URL no longer fails the page

This pull request stops a stale or bookmarked URL that names a deleted portlet from failing the whole page with a 500, by catching the IllegalArgumentException that the portlet window lookup throws while UrlSyntaxProviderImpl parses pP_ parameters.

uPortal-Project/uPortal PR 2924 at dc19c65, explained 2026-11-16. References link to this commit.

Background

New to this area? Expand for the deeper background.

uPortal is a web portal: one page that shows several small applications side by side. Each application is a portlet. uPortal keeps three objects for each portlet:

  • A portlet definition is the published portlet, such as a news reader. It has a numeric id.
  • A portlet entity is one user's subscription to a definition. It sits at a node in that user's layout, the saved arrangement of their page.
  • A portlet window is what uPortal renders for an entity. When a URL says which portlet a parameter is for, it names a window.

Several portlets share one page, so uPortal writes each portlet's state into the query string, with prefixes that say which portlet a parameter belongs to. A bookmark keeps that query string exactly as it was.

A servlet filter wraps a request on its way in and out. When code beneath it throws an exception that nothing catches, the exception climbs out through the filters and the servlet container answers with HTTP status 500.

In Java, IllegalArgumentException is an unchecked exception. A method may throw it without declaring it, and no caller is forced to catch it.

uPortal logs through SLF4J. A call such as logger.warn("id '{}': {}", a, b) fills each {} with the next argument. When the last argument is an exception with no {} left for it, SLF4J prints that exception's stack trace after the message.

The tests use JUnit 4 and Mockito. @Ignore on a test class makes JUnit skip every test in it. @RunWith(MockitoJUnitRunner.class) creates the @Mock fields before each test. It also fails the class when a test sets up a stub with when(...) that the test never uses. MockitoJUnitRunner.Silent does the same setup without that unused-stub check. A stub written when(call).thenThrow(exception) makes the mock throw when the code under test makes that call.

The pull request body gives the case: a URL carrying pCa=27_ctf9_142032 after portlet definition 27 was deleted. It carries the fix from PR 2916, made on rel-5-17-patches, forward to master.

The class that reads these URLs is UrlSyntaxProviderImpl. It uses a few strings from PortalConstants: the separator _ as SEPARATOR (PortalConstants.java:4), the portlet-parameter prefix pP_ as PORTLET_PARAM_PREFIX (PortalConstants.java:8), pCa (PortalConstants.java:11), and pCs, the window-state parameter (PortalConstants.java:15). The values of pCa are, in the class's own comment, "the set of portlet window ids that also have parameters on the url". pCs is one of the control parameters: names under the pC prefix that set something about a window, such as its state, and may end in that window's id.

A window id string such as 27_ctf9_142032 has three parts joined by underscores (PortletEntityIdStringUtils.java:55-58). The registry reads the same string as a portlet entity id, which is why the new tests call it staleEntityId.

The first new test builds its input from these pieces, so a URL shaped like it carries pCa=27_ctf9_142032 and a parameter named pP_27_ctf9_142032_implicitModel. That name reads: a portlet parameter, for window 27_ctf9_142032, called implicitModel.

The entry point is getPortalRequestInfo (UrlSyntaxProviderImpl.java:279). It collects the pCa values into a set of strings, additionalPortletIds (UrlSyntaxProviderImpl.java:551-556). Then the parameter loop walks every remaining query parameter (UrlSyntaxProviderImpl.java:565-678). A name that starts with pP_ goes to parsePortletParameterName (UrlSyntaxProviderImpl.java:587-589). A control parameter such as pCs_27_ctf9_142032 goes to parsePortletWindowIdSuffix (UrlSyntaxProviderImpl.java:652-654). Both helpers ask portletWindowRegistry.getPortletWindowId to turn a window id string into an IPortletWindowId, the typed id of a portlet window.

parsePortletParameterName returns a Tuple<String, IPortletWindowId>, uPortal's pair type. Its first is the parameter name the portlet will see. Its second is the window the parameter belongs to, or null when the name holds no window id the parser recognizes. To the caller, null means "for the targeted portlet": the portlet the URL path names, whose request data the parameter loop holds in targetedPortletRequestInfo. The helper safeSubstringAfter returns everything after a prefix.

Key concept An id in pCa is only a string. The parser uses it to find a window id inside a parameter name. Nothing checks that the id still resolves until the registry lookup runs.

That lookup is where a stale id fails. PortletWindowRegistryImpl.getPortletWindowId (PortletWindowRegistryImpl.java:293) passes the id to PortletEntityRegistryImpl, whose parseConsistentPortletEntityId (PortletEntityRegistryImpl.java:733) checks each part and throws IllegalArgumentException when one does not resolve. For a deleted definition the message reads "No parent IPortletDefinition found for 27 from entity id string: 27_ctf9_142032" (PortletEntityRegistryImpl.java:758-762). The interface's javadoc lists that exception only for a null id (IPortletWindowRegistry.java:119-126), so a caller reading only the interface gets no warning of this case.

getPortalRequestInfo has no catch, so an exception from the parameter loop reaches ExceptionLoggingFilter, which every URL passes through. The filter logs it at ERROR with the URL and rethrows it (ExceptionLoggingFilter.java:60-67).

The diff leaves two other catches of this exception unchanged: one in parsePortletWindowIdSuffix (UrlSyntaxProviderImpl.java:945-953), and one in the handler for the delegate-parent parameter (UrlSyntaxProviderImpl.java:116-129). With the new one, they are the three places the parameter loop calls getPortletWindowId to turn an id string into a window id. The call for pP_ names was the one without a catch.

The pull request also lowers two log lines outside URL parsing. ClassicMaxInactiveStrategy.calcMaxInactive works out a user's session timeout from MAX_INACTIVE permissions, and MaxInactiveFilter calls it. PersonalizerImpl.createTokenMappingForPerson builds a map with one token per person attribute, for substitution into personalized text.

Intuition

A URL is written while its portlets exist and replayed later, maybe after the portlet definition it names is deleted. A parser that meets an id it can no longer resolve can fail the request, or it can drop the window id from that one parameter and carry on. Before this change, parsePortletParameterName had no catch, so the registry's exception went straight through it.

The method already had an answer for a name whose window id it could not use. When the id in the name is not listed in pCa, it returns the name with a null window id and lets the caller decide. The fix sends a failed lookup to that same answer. The method's own loop runs over additionalPortletIds and looks for each id inside the name. For pP_27_ctf9_142032_implicitModel it finds 27_ctf9_142032, and paramName becomes implicitModel, the text after pP_, the id, and the separator. Before the change, the lookup and the return sat straight in that loop's body, so the registry's exception left the method.

Now the lookup and the success return sit inside try. The catch logs a warning and does not return, so the method's loop moves on to the next listed id. When no other id matches, control reaches the fallback at the end of the method (UrlSyntaxProviderImpl.java:922-923). That fallback is the second row of the Intuition table: strip only pP_ and return a null window id. The implicitModel value of paramName is thrown away.

The warning puts e.getMessage() into a {} placeholder, so the log line carries the registry's message and no stack trace. The older catch in parsePortletWindowIdSuffix passes the exception itself as the last argument (UrlSyntaxProviderImpl.java:948-952), so its warning prints the trace.

A null window id sends the value to the targeted portlet's parameters, keyed by the name the method returned. When the request targets no portlet, the caller logs a second warning, removes the parameter, and stops. Neither branch throws, so the request no longer takes the path to the 500.

Edge case In the branch for a request that targets no portlet, the break (UrlSyntaxProviderImpl.java:603) leaves the whole parameter loop, not just this parameter. Parameters the loop has not reached yet skip the portlet parsing. The block after the loop then hands them on as unparsed parameters, which with no portlet targeted usually means the portal's own parameter map, where u_ parameters go (UrlSyntaxProviderImpl.java:681-719). That break predates this pull request. A stale pP_ parameter can now reach it.

Quiz

A bookmarked URL targets a working portlet and also carries pCa=27_ctf9_142032 and pP_27_ctf9_142032_implicitModel=true. Definition 27 has been deleted. After this pull request, what does the targeted portlet receive?

The catch logs and lets the loop finish, so the method reaches its fallback, which strips only pP_ and returns a null window id. The caller reads null as "for the targeted portlet" and stores the value under the returned name, stale id included. Getting implicitModel would need the id stripped as well, which only the success path does. The warning says the parameter will be ignored, yet the caller still stores it, because the method dropped only the window id.

The new catch names IllegalArgumentException instead of RuntimeException. Why does the narrower type matter?

Each registry throw site for an id that does not resolve uses IllegalArgumentException, so the catch covers the stale-URL case. A bug inside the lookup, such as a NullPointerException, still escapes to ExceptionLoggingFilter and is logged at ERROR with its stack trace. The exception is unchecked, so the compiler demands no catch at all. The filter runs outside this method, so no catch here could touch its response. Every exception has getMessage().

Which rewrite of the new catch block would still pass both new tests?

The tests assert only that a pair comes back and that its window id is null. Returning (paramName, null) satisfies both, yet paramName already has the stale id cut off, so the targeted portlet would receive implicitModel instead of 27_ctf9_142032_implicitModel. A rethrow fails because the call must not throw, a null return fails assertNotNull, and a placeholder window id fails assertNull.
